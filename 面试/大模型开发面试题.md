2. ### 在接受参数时，*args 和 **kwargs的区别是什么
    

`*args`: 接收任意数量的非关键字参数并打包成元组。

`**kwargs`: 接收任意数量的关键字参数并打包成字典。

函数接收实参，按顺序分配给形参，但遇到带*的形参时，就把未分配出去的一起以元组 or 字典形式打包分配给带星号的参数。

3. ### 装饰器、生成器、迭代器、列表推导式？上下文管理器？
    

**装饰器**：用来修改或扩展函数方法的高阶函数，接受一个函数作为参数并且返回另一个函数，而不需要修改源代码。例如代码重用、日志记录、性能计时

**生成器**：通过 yield 语句生成一个值。它不会一次返回所有的值，而是每次请求一个值时才生成一个。这种惰性求值可以节省内存。（流式输出）

**迭代器**：实现了 iter 和 next 方法，它允许我们遍历一个集合而不需要暴露集合的内部结构。（例如生成器本身就是一个迭代器）。

**列表推导式**：一般是由一个表达式 + 可选条件 + for 语句构成，用一种简洁的方式来创建基于某种逻辑的列表。squares = [x**2 for x in range (5)]

**上下文管理器**：通过 with 语句来实现，主要用来自动管理资源，保证用完后能正确释放，比如文件读写和数据库连接等

4. ### 在python中，深拷贝和浅拷贝的区别是什么
    

浅拷贝是指复制对象的最外层结构，内部引用共享。copy.copy()

深拷贝是递归复制内部的所有元素及其可变对象。copy.deepcopy()

比如创建一个列表嵌套列表，分别使用两种拷贝方法，然后在嵌套列表里面添加一个元素，print结果，会发现，浅拷贝里面的嵌套列表也增加了这个元素，但深拷贝没有。

**浅拷贝：**

- 对象内部元素是不可变对象，或不关心内部共享。
    
- 如：复制配置模板，树结构的节点引用
    

**深拷贝：**

- 当对象内部含有可变对象，并且需要完全独立修改，避免改动相互影响
    
- 如：复制嵌套列表、复杂JSON配置

9. ### 简述一下向量数据库的原理？
    

向量数据库的核心原理就是将文本图像此类非结构化数据转为为高维空间的向量, 通常来讲, 语义相似的的内容在向量空间距离更近.

由于企业级数据库存储的数据量很大, 所以在检索的时候往往采用的是ANN 快速近似最近邻搜索, 通过构建索引结构, 快速定位候选集选取出top-k

主流的ANN算法包括HNSW原理是构建多层图, 高层负责搜索范围, 底层则是精细搜索,

IVF+PQ原理则是先聚类再压缩, 将向量分成多个簇, 查询时只搜附近的几个簇

11. ### 你是如何理解相似度索引的？
    

相似度检索本质上是寻找语义相似的结果，核心思想是将数据转化为高维向量，通过计算向量间数学距离衡量相似性。

它的原理是：他会先通过一个模型选择使用不同的相似度度量（余弦相似度-文本，欧式距离-图像常用，内积）将数据转换为向量，最后进行索引加速，然后查询执行

主流的索引类型：

- FLAT：最简单的索引方式，进行暴力搜索，可以保证精确度，但效率低，尤其在数据量大时。**适合在小型、百万级数据集上寻求完全精确的搜索结果**
    
- IVF_FLAT：一种基于聚类和倒排索引来进行数据存储和检索的方法，广泛用于在**大规模数据集上实现高效的近似最近邻搜索**
    
- IVF_PQ：一种高效的向量索引方式，结合了倒排文件索引和乘积量化技术，旨在加速大规模高维数据集的检索
    
- HNSW：基于图的索引，最适合对搜索效率有高要求的场景

19. ### LangChain和LangGraph两个框架有什么优缺点？
    

LangChain是一个通用的智能体编排工具，它把工作编排成一系列的工作节点，用一条工作链把这些节点连接起来，组织成一张有向无环图(DAG)

它的工作方式适合比较简单的智能体（比如：提示词-->调用模型-->结果优化），一旦涉及到一些复杂的流程，就有些力不从心了

LangGraph是由LangChain团队开发的开源框架，专为构建基于大型语言模型(LLM)的有状态、多参与者应用程序而设计

其核心创新在于采用图结构(Graph)作为计算模型，突破了传统有向无环图(DAG)的限制，支持循环工作流和动态状态管理

用节点（Node）表示任务步骤，用边（Edge）连接节点，并通过状态（State）在不同节点之间传递信息

  

14. ### LangChain处理长文本和多轮对话的内部优化机制
    

LangChain处理长文本和多轮对话，核心就是围绕 LLM 上下文窗口有限这个痛点，我从两大块来说：

1. **对于长文本处理的优化机制**
    

文本分块**：**把超长文档按语义层级拆分，用递归分块器保证段落连贯，块之间加重叠避免信息断裂，再给块加元数据方便后续检索。

使用RAG把文本向量化存入向量库，问答时只召回最相关片段，而不是把全文塞给模型，从根源解决超长文本问题

2. **对于多轮对话的记忆管理机制**
    

为了让会话历史中保留核心的信息，而又不至于内容太多，我们可以采用下面几种策略

- **滑动窗口记忆：**只保留最近 N 轮对话，控制token不爆炸
    
- **摘要记忆：**历史太长时，自动用 LLM 把旧对话压缩成摘要，只保留最近几轮完整内容
    
- **摘要 + 窗口混合记忆：**近期完整保存、远期摘要合并，平衡细节与长度
    
- **向量检索记忆：**把历史对话向量化，变成 “长期记忆”，需要时再召回，实现近乎无限轮对话
    

总之一句话，就是尽量只保留跟当前问题相关的内容和历史发送给大模型

  

15. ### 假设现在让你基于Function calling制作一个天气查询的功能, 后端代码如何写?
    

基于Function calling做天气查询的后端核心逻辑分4步：

1. **定义函数描述**：定义天气查询函数的入参（城市、日期）、出参（温度、天气状况）
    
2. **调用大模型**：把用户提问 + 函数描述传给大模型，让模型判断是否需要调用天气函数，并返回标准化的调用参数
    
3. **执行本地函数**：解析大模型返回的调用参数，调用真实的天气 API（可以对接高德）获取数据
    
4. **结果回填**：把天气数据传给大模型，让模型生成自然语言回答，返回给用户
    

  

5. ### 如果要做到人机交互的之类的体验, 如何在langgraph上面体现出来?
    

要在LangGraph上做出自然流畅的人机交互体验，主要就三点：

1. **把交互做成一个节点：**流程跑到需要问用户、确认信息的时候，就加一个**人工交互节点**，让流程暂停，等用户输入。
    
2. **用状态保存上下文：**所有对话信息、用户回答、中间结果，都存在统一的 **State** 里，这样多轮交互不会断，上下文一直连贯
    
3. **用条件边控制什么时候找人：**比如信息不全、不确定、需要确认时，就让流程自动走到**交互节点**问用户；信息够了就直接往下执行
    

整体一句话：**在工作流里插交互节点，用状态存上下文，用条件判断什么时候问用户，就能做出自然的人机交互**

  

17. ### 聊一聊SpringAI和langchain之间的区别
    

Spring AI 和 LangChain 核心都是大模型应用开发框架，但定位、生态、使用场景完全不同

1. **首先，二者的定位和出身不一样**
    
    1. LangChain是**通用型大模型编排框架**，核心解决LLM + 外部工具（检索、函数调用、记忆）的组合问题，更灵活
        
    2. SpringAI 是**Spring生态专属的大模型框架**，本质是把大模型能力融入 Spring 体系，更贴合企业级 Java 开发
        
2. **其次，适用场景也不一样**
    
    1. LangChain适合做灵活的 AI 原生应用（比如多轮对话、RAG 问答、智能体），它的记忆、检索、流程编排能力更成熟
        
    2. Spring AI适合做企业级 Java 后端 + 大模型的融合应用，特别适合在原有Java程序的基础上添加大模型的场景，不用改原有技术栈，学习成本低
        

总结来看，就是LangChain不限技术栈，灵活但和企业级后端整合成本高；Spring AI只服务Spring开发者，适配企业级开发，上手快、整合成本低

3. ### RAG的原理是什么？
    

RAG，就是检索增强生成，之所以使用它是因为，大模型有两个典型的缺点就是：知识更新延迟和领域知识缺失

为了解决这这两个问题，就有RAG技术，它的做法是在调用大模型的时候，需要将跟问题相关的资料提取出来一起发给大模型，进而提高问题回答准确性

它的整个流程分为这样几步：

1. 将公司内部的一些资料文档向量化之后存储到数据库备用
    
2. 当用户提问时，先将用户问题通过嵌入模型向量化，然后从向量数据库中召回相关文档
    
3. 将召回的文档和用户的原始问题一起拼装为提示词，然后发送给大模型
    
4. 大模型基于增强后的提示词来输出答案

7. ### BM25算法原理是什么
    

答案:

BM25是一种用于信息检索的排序算法, 用来衡量一个查询与文档之间的相关性得分

它是TF-IDF的改良版, 常被用于搜索引擎比如ES

所谓TF-IDF是指词频-逆文档频率, 它有两个严重缺陷:

- 词频线性增长: 当一个词反复出现时, 会让其的分数直线增长
    
- 长文档: 长文档天然包含更多词，更容易命中查询词, 短文档得分先天劣势
    

而BM25的核心思想: 对词频进行非线性压缩, 并对文档长度做归一化

首先就是高频词汇的得分会逐渐趋近于k1 + 1 (不再增长), 而文档长度归一化后长文档的得分会降低, 至于IDF部分加入的平滑项避免了除零问题

6. ### 如果错误发生在LangGraph工作流的中间步骤（比如调用高德地图 API 失败），如何利用Checkpoint机制实现“断点续传”或“状态回滚”？
    

LangGraph 的 Checkpoint 机制本质是**持久化工作流的状态快照**，包含：

1. 工作流当前执行到的节点
    
2. 所有已完成步骤的状态数据
    
3. 对话 / 工作流的上下文信息
    

实现 “断点续传” 和 “状态回滚” 的核心逻辑是：

- **断点续传**：出错时保存当前最新的有效 Checkpoint，恢复时从该 Checkpoint 加载状态，跳过已成功执行的步骤，直接从出错节点重新执行。
    
- **状态回滚**：出错时放弃当前错误状态，加载上一个成功步骤的 Checkpoint，回到出错前的状态，可选择重试该步骤或调整逻辑后重新执行。
    

7. ### 当使用fastapi承载大模型接口时，你是如何处理那些可能阻塞事件循环的操作的？比如涉及到外部io模型推理或者耗时的数据处理时？你采取过哪些方式来避免阻塞主事件循环？
    

FastAPI 基于异步的 Starlette 框架，其高性能依赖于**非阻塞的事件循环**。一旦有同步阻塞操作（如 CPU 密集型计算、无异步接口的外部 IO 调用）占用事件循环，会导致整个服务的并发能力急剧下降。解决思路分为三类：

1. **异步化改造**：优先使用异步库替代同步库，让 IO 操作让出事件循环。
    
2. **线程 / 进程池隔离**：将阻塞操作放到独立的线程 / 进程池中执行，避免占用主事件循环。
    
3. **服务拆分**：将重度阻塞的操作（如大模型推理）拆分为独立服务，通过消息队列异步调用。
    

  

### 问题七: 构建智能体流程的过程中，当系统需要连续经过多个节点才能得到最终结果时，你是如何确保用户能够尽快看到内容的？比如在请求还没完全结束之前，系统是否会提前输出部分结果？或者采取其他方式来提升游戏体验，请结合你当时的实际做法来讲一讲

答案:

在构建智能体流程时，我主要从三个方面保障用户体验：流式输出、分阶段反馈、并行处理与降级策略。

第一，启用流式输出。我们基于 HTTP/1.1 的 `Transfer-Encoding: chunked` 实现了流式响应。当大模型开始生成 token 时，我们就以小数据块的形式逐个返回，用户可以立刻看到‘打字机’效果，避免长时间空白等待。LangChain 通过 `.stream()` 和 LCEL 对此做了封装

第二，分阶段输出中间结果。对于多步骤任务（如‘检索 → 分析 → 总结’），我们不会等到全部完成才返回。例如，在检索阶段完成后，先返回‘正在分析文档…’这类友好提示；分析完成后，再展示初步结论。这样用户始终知道系统在做什么。

第三，关键任务并行化(异步)。如果多个子任务是独立的（如同时调用天气 API 和交通 API），我们会并行执行，并采用‘谁先完成先展示’的策略，提升整体感知速度。

第四，设置降级策略兜底。若某环节超时未完成，我们返回简化版答案或默认提示（如‘信息获取中，请稍后重试’），防止用户卡死。

### 什么是“意图-动作状态机”，并说明它在对话系统中的作用。结合大模型（LLM），你是如何实现这种状态机的？

答案：

意图-动作状态机’是一种用于管理任务型对话流程的设计模式，其核心思想是：

将整个对话拆分为若干明确的状态（如‘询问出发地’、‘确认订单’），每个状态对应一个用户意图阶段。当用户输入新消息后，系统根据当前状态 + 用户内容，决定：

- 下一步进入哪个状态
    
- 执行什么动作（如追问信息、调用工具、结束对话）
    

一共解决了三个问题

1. 保证流程可控：按业务规则一步步走，避免遗漏关键信息；
    
2. 提升成功率：在预设路径上引导用户，减少幻觉或无效回复；
    
3. 便于维护和测试：每个状态逻辑独立，新增/修改不影响整体
    

在实际项目中，我们使用 LangGraph 来实现这种状态机：

- 每个状态是一个 `Node`（如 `ask_departure`, `confirm_booking`）
    
- 每条边是 `ConditionalEdge`，由 NLU 输出决定跳转
    
- 全局 `State` 存储槽位、对话历史、当前阶段
    
- 支持循环（如多次追问）、异常处理（fallback）
    

例如，当用户说‘我想订机票’，NLU 识别为 `intent=book_flight`，触发从 `start` → `ask_departure` 的转移；若用户输入‘上海’，则槽位填充成功，进入下一状态

### 问题六: 谈一谈对MCP协议的理解

答案:

MCP，全称 Model Context Protocol（模型上下文协议），是一种开放标准协议，目标是为了解决大语言模型（LLM）与外部工具、数据源和服务之间通信不统一、集成成本高、生态割裂的问题。

工具或服务实现了 MCP 协议，任何支持 MCP 的 LLM 应用（比如智能助手、IDE 插件、多智能体系统）都能即插即用，无需重复开发适配逻辑

由于大模型缺乏记忆, 并且本身训练时使用的数据存在过期等问题, 传统做法使用工具封装没有统一标准, 返回的数据结构各种各样. 而MCP协议很好低解决了这个问题

MCP的核心架构一共有四种

1.Host(主机): 就是LLM应用本身

2.Client(客户端): 负责与Server建立连接

3.Server(服务器): 独立运行的工具服务, 提供三类资源Tools, Resources, Prompts

4.Base Protocol(基础协议): 一般支持三种消息类型 Request/Response (同步调用),

Notification: 异步事件, 支持Stdion(本地)和SSE/HTTP远程两种传输方式

它的优势在于:

标准化：所有工具暴露schema统一, 大模型更易理解

可复用: 一个MCPserver可被多个智能体同时调用

动态发现: 智能体启用时可以自动获取可用工具列表, 无需硬编码

#### 延申: MCP和常见的网络协议的区别在哪里?

答案:

MCP(Model Context Protocol)是一种面向LLM应用的高层协作协议, 他的目的是将大模型和外部工作,数据源之间的交互标准化. 不同于HHTP等网络协议, MCP解决的的是"模型如何理解, 并调用外部能力完成复杂任务", 后者更多低关注于"如何传输数据"

### 问题七: MCP协议中, Resource和Tool的区别

答案:

在MCP协议中, tool和Resource都由MCP Server提供

定义上来讲, tool属于可执行的操作函数, LLM调用tools时会产生后续的影响比如修改数据等. 而Resource则是可读取的数据片段, LLM使用Resource时往往只是读取数据.

使用场景上来说, 使用tool时往往会有返回值, 而Resource值只是用于上下文注入

**延申: 如何做数据脱敏?**

MCP原生就支持基于URI的细粒度权限空值, 设置了权限白名单, 只有符合白名单的才允许访问, 其次即使有权限也要做数据脱敏, 原始敏感数据不会直接返回而是采用类似于掩码的格式返回诸如手机号一类的数据, 同时MCP Client在请求resource可以携带上下文元数据, Server也可以代码做校验决定用户是否可以访问. 大模型的prompt不可以直接拼接敏感信息, 必须是大模型显式请求而且通过client的校验才允许

21. ### Transformer原理是什么？自注意力机制？多头注意力机制？（待修订）
    

2017年的夏天，一篇名为[《Attention is all you need》](https://arxiv.org/abs/1706.03762)的论文横空出世，并在接下来的几年内直至现在制霸了整个生成式AI领域，8名研究学者首次提出了Transformer这种神经网络架构，其独特之处在于完全基于注意力机制，摒弃了传统的循环和卷积操作。通过[自注意力机制](https://zhida.zhihu.com/search?content_id=244417806&content_type=Article&match_order=1&q=%E8%87%AA%E6%B3%A8%E6%84%8F%E5%8A%9B%E6%9C%BA%E5%88%B6&zd_token=eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJpc3MiOiJ6aGlkYV9zZXJ2ZXIiLCJleHAiOjE3NzA0NjkzMTIsInEiOiLoh6rms6jmhI_lipvmnLrliLYiLCJ6aGlkYV9zb3VyY2UiOiJlbnRpdHkiLCJjb250ZW50X2lkIjoyNDQ0MTc4MDYsImNvbnRlbnRfdHlwZSI6IkFydGljbGUiLCJtYXRjaF9vcmRlciI6MSwiemRfdG9rZW4iOm51bGx9.9pzE6asRHV-dmJMaR8oQpZh92A8uKXcmc0zIWg4Hl9Q&zhida_source=entity)（self-attention），Transformer能够有效捕捉输入序列中的长距离依赖关系，使得模型在处理长文本时更为高效和准确。[多头注意力机制](https://zhida.zhihu.com/search?content_id=244417806&content_type=Article&match_order=1&q=%E5%A4%9A%E5%A4%B4%E6%B3%A8%E6%84%8F%E5%8A%9B%E6%9C%BA%E5%88%B6&zd_token=eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJpc3MiOiJ6aGlkYV9zZXJ2ZXIiLCJleHAiOjE3NzA0NjkzMTIsInEiOiLlpJrlpLTms6jmhI_lipvmnLrliLYiLCJ6aGlkYV9zb3VyY2UiOiJlbnRpdHkiLCJjb250ZW50X2lkIjoyNDQ0MTc4MDYsImNvbnRlbnRfdHlwZSI6IkFydGljbGUiLCJtYXRjaF9vcmRlciI6MSwiemRfdG9rZW4iOm51bGx9.aXtVeWn5Jg8d04JPZdePkiQmTWua39_A1drVK35Tm60&zhida_source=entity)（multi-head attention）则进一步增强了模型的表达能力，使其能够同时关注输入序列中的不同部分，捕捉更加复杂的语义关系。

答案:

Transformer的核心是自注意力机制, 对输入序列中的每个位置，计算它与其他所有位置的相关性（注意力权重）

它会先用分词工具将句子拆分为最小的语义单位, 做一个向量, 因为 Transformer 没有 RNN/CNN 的顺序结构，所以通过加入位置编码（如正弦/余弦函数或可学习的位置嵌入）来注入序列顺序信息

Encoder-Decoder 架构：

- Encoder：堆叠 N 层，每层包含 Multi-Head Attention + 前馈网络（FFN），带残差连接和 LayerNorm。
    
- Decoder：类似 Encoder，但增加了一个“Encoder-Decoder Attention”层，用于关注 Encoder 的输出。

22. ### 解释一下维度是什么？ （优化）
    

答案：

N维’指的是向量的维度（dimension），即它由 N 个浮点数组成，代表语义在N 维空间中的坐标。

而‘向量的长度’（length），在数学上叫 L2 范数，计算公式是各分量平方和的平方根。

但在实际 NLP 应用中，绝大多数 embedding 模型（如 OpenAI、BGE、Sentence-BERT）会将向量归一化

因此，在语义搜索或 RAG 系统中，我们计算相似度时直接用点积（等价于余弦相似度），而不会使用向量长度本身作为特征。

量化感知训练: 在微调阶段模拟量化噪声, 在训练时就要插入"伪量化" 操作, 缺点是需要训练数据和训练时间, 用于关键业务模型

仅权重量化: 只量化权重, 计算时再转回来, 现代GPU支持INT4/8对FP16的快速反量化

### (待优化)问题十六: VLLM的原理是什么? 它是如何做到提升推理效率的?

答案:

vLLM 的核心是通过 PagedAttention 和 Continuous Batching 两大技术创新，解决大模型推理中的显存碎片和GPU 利用率低问题。

第一，PagedAttention 借鉴操作系统分页机制，将 KV Cache 拆分为非连续的内存块（block），通过索引表动态拼接。大幅提升显卡利用率，显著增加并发能力。

第二，Continuous Batching 打破传统‘静态批处理’限制，允许在推理过程中动态插入新请求，并智能混合 prefill（计算密集） 和 decode（内存密集） 任务，使 GPU 利用率接近饱和。

此外，vLLM 还集成了 前缀缓存（避免重复计算公共前缀）、推测解码（用小模型草稿加速生成）、CUDA Graph（降低 kernel 开销）等优化。

在我们项目中，使用 vLLM 部署 后，吞吐量提升K 倍，P99 延迟降低 M%，单卡成本下降 N%
