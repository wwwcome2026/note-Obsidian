## 使用说明

> [!important] 这不是让你机械背诵的标准答案 先把文中的 **【待补充】** 替换为真实信息，再用自己的语言复述。凡是没有亲自实现、无法画出流程或无法解释异常处理的模块，应把"负责"改成"参与"，不能把架构图中的全部组件都说成个人独立完成。

回答项目题时统一采用四步：先说业务目标，再说个人职责，然后讲核心实现，最后说结果、限制或改进。技术题先给结论，再解释原理和项目中的实际取舍。

## 面试官看完简历后首先会核验的事项

> [!warning] 高频风险点 面试前请逐一核对并准备好回答，以下都是面试官的"火力侦察区"。

1.  **2022 年 3 月开始工作、2023 年 6 月毕业**，两段时间如何重叠，是实习、校企合作还是全职。\
2.  **4 年经验由约 2 年 Java 和约 2 年 Agent/RAG 构成**，转型过程是否真实、是否有代码深度。\
3.  **A2A 协议公开时间较晚**，需要说明项目采用 A2A 的准确时间、SDK 版本和此前架构。\
4.  **智询通 Agent 中台 涵盖网关、LangGraph、A2A 控制面、任务中心、Tool、RAG、SSE 和可观测性**，必须明确个人边界。\
5.  **Event Bus、Persistent TaskStore、Task Guard、AgentCard Center** 是否真实落地，分别用了什么存储和组件。\
6.  **"ToolResult 是标准 A2A 事件"表述不严谨。** 工具结果通常映射为 Message Part、DataPart、Artifact 或平台自定义事件。\
7.  **PostgreSQL Checkpoint 是图执行状态持久化，不等于完整长期记忆。**\
8.  **SSE 断线恢复一般只能回放保留窗口内的事件，不能保证从任意 token 无损续跑。**\
9.  **RailOps 项目中的铁路标准编号**在简历中截断为"TB/T 2834-201"，面试前应核对并修正为真实完整编号。\
10. **WMS 中"思考过程处理"**容易被理解为展示模型原始思维链，应改成"生成阶段状态或可解释摘要"，不要声称展示隐式推理过程。\
11. **"经压测保持稳定""降低交付周期"等表述缺少数字**，必须准备真实的并发量、P95/P99、错误率或前后对比。\
12. **OpenTelemetry、RAGAS、BERT、Unlimited OCR** 等技术写在简历里，就要能说清具体用法，不能只解释定义。

### Q011｜请用 1 分钟介绍 智询通 Agent 中台。
> [!note] 候选人逐字稿 这是面向在线教育场景的多智能体协同中台，统一处理课程推荐、购课、课程咨询和知识问答。请求经过网关和会话中心后，由 LangGraph 完成上下文装载、意图路由和任务编排，再通过 A2A 调用独立业务 Agent。Agent 通过受控 Tool 访问课程或交易微服务，KnowledgeAgent 调用 EduRAG；文本、工具结果、引用和任务状态最终统一转换为 SSE 返回前端。我的核心职责是 **【真实模块】**。

### Q012｜请画出一次请求的完整链路。
> [!note] 候选人逐字稿 用户请求先经过 Nginx 和业务网关，再进入 agent-center-gateway 做鉴权、限流和路由。编排中心创建 RequestContext，按 sessionId 装载会话状态，LangGraph 识别意图并选择 Agent，然后 A2A Client 创建或关联 Task。下游 Agent 可以通过 Tool Gateway 调业务服务，也可以调用 EduRAG。事件聚合层把 Message、Artifact、工具结果和 TaskStatus 映射为前端事件，经 SSE 逐步返回。requestId、traceId、taskId 和 contextId 用于串联链路。

### Q013｜你在这个项目里到底写了哪些代码？
> [!note] 候选人逐字稿 我独立负责的是 **【列出真实仓库、包或类】**，例如 **【RequestFilter、ChatRouter、LangGraph 图、A2A Client、SSE Event Gateway、KnowledgeAgent】** 中的部分。我参与了 **【接口设计或联调模块】**，但 A2A 控制面、网关或业务微服务如果不是我实现的，我会明确说明。判断标准是我是否能说出类结构、表结构、异常分支和一次实际排障。

### Q014｜为什么拆成多个 Agent，不使用一个 Agent 加很多 Tool？
> [!note] 候选人逐字稿 当工具少、权限一致时，单 Agent 更简单。这个项目中推荐、购买、咨询和知识问答的 Prompt、数据权限、工具集合、超时策略和发布节奏不同，所以按业务边界拆分。这样可以限制每个 Agent 的 Tool allowlist，并单独扩容和回滚。代价是任务协议、状态管理和链路排查更复杂，因此拆分是基于治理需求，不是为了追求多 Agent 形式。

### Q015｜多 Agent 和普通微服务调用有什么本质区别？
> [!note] 候选人逐字稿 普通微服务输入输出相对确定，一次请求通常同步完成；Agent 任务可能长耗时、多轮、需要补充信息，并持续产生消息和 Artifact。A2A 为能力发现、任务状态、消息交换和流式更新提供统一契约。不过确定性的库存扣减或订单写入仍由普通业务服务和 Tool 完成，不会全部包装成 Agent。

### Q016｜为什么使用 LangGraph，不直接写 if/else？
> [!note] 候选人逐字稿 简单流程用 if/else 更合适。这个项目包含上下文装载、条件路由、外部 Agent 调用、工具调用、重试、等待和恢复，使用状态图更容易表达分支和恢复边界。LangGraph 的价值是显式 State、节点、条件边和 Checkpoint，不是代码看起来更高级。外部副作用仍要由业务幂等保证，Checkpoint 不会自动解决事务问题。

### Q017｜LangGraph State 中有哪些核心字段？
> [!note] 候选人逐字稿 我们按身份、会话、路由、任务和输出分类保存状态，典型字段包括 tenantId、userId、sessionId、requestId、messages、summary、intent、selectedAgent、taskId、contextId、artifacts 和 errorContext。敏感 Token 和大体量业务数据只保存引用或短期使用。实际字段以 **【真实 State 模型】** 为准，我会重点解释各节点读写哪些字段。

### Q018｜节点是如何划分的？
> [!note] 候选人逐字稿 我按职责和可恢复边界划分为请求过滤、上下文装载、意图路由、A2A 任务提交、事件聚合和安全后处理。外部 Agent 调用单独做节点，因为它可能超时并需要查询状态或恢复。节点过细会增加 State 传递和调试成本，过粗又无法利用条件分支和 Checkpoint，所以以"是否有独立输入输出和失败策略"为划分依据。

### Q019｜PostgreSQL Checkpoint 如何恢复会话？
> [!note] 候选人逐字稿 LangGraph 使用 thread_id 关联一条执行线程，在关键节点把 State 和执行位置写入 PostgreSQL。下一轮请求携带同一业务会话标识时，可以加载最近 Checkpoint 并继续构建上下文。thread_id 必须包含租户和用户隔离信息，参考稿使用 sessionId；是否还拼接 tenantId 和 userId **【待补充】**。Checkpoint 保存图状态，不等于长期记忆；聊天历史、摘要和用户偏好需要单独设计生命周期。

### Q020｜Checkpoint 和长期记忆有什么区别？
> [!note] 候选人逐字稿 Checkpoint 面向图执行恢复，记录运行到哪个节点以及当时 State；聊天历史是消息记录；长期记忆是经过筛选的偏好、摘要或结构化事实。它们的数据量、有效期和读取策略不同。这个项目实际实现到 **【真实范围】**，如果只做 Checkpoint 和消息窗口，我不会声称已经实现完整长期记忆。

### Q021｜同一会话并发发送两个问题，状态会不会覆盖？
> [!note] 候选人逐字稿 必须对同一 thread 的并发写做约束。实际采用 **【串行队列/分布式锁/版本号 CAS/每轮独立 runId】** 中的 **【真实方案】**。如果允许并行，提交 Checkpoint 时要检查版本并定义消息合并规则；如果项目依赖前端串行发送，也要明确这是当前约束和已知风险。

### Q022｜节点失败后如何恢复？
> [!note] 候选人逐字稿 先区分可重试和不可重试错误。连接超时等瞬时错误可以有限重试，参数、权限和业务拒绝不重试。对于外部写操作，恢复前先通过 taskId 或业务幂等键查询执行状态，不能直接重跑整个节点。Checkpoint 帮助恢复编排状态，但下游副作用必须由业务服务的唯一约束或状态机兜底。

### Q023｜意图路由是纯模型判断吗？
> [!note] 候选人逐字稿 不是。我们先做基础规则和上下文判断，再让模型按结构化 Schema 输出意图和置信度，最后结合 Agent 可用性、租户权限和必填字段做二次校验。低置信度或缺少信息时进入 UnknownAgent 或澄清流程，涉及购课等写操作时阈值和确认要求更严格。模型名称和阈值 **【待补充】**；评估集记录真实问题、期望 Agent、实际 Agent 和原因，每次新增 Agent 或修改 Prompt 后做回归并重点查看混淆矩阵。

### Q024｜如何避免模型路由到无权限 Agent？
> [!note] 候选人逐字稿 权限不能只靠 Prompt。路由候选集先根据租户、用户和 Agent 策略过滤，选中 Agent 后还要在 A2A Gateway 和 Tool Gateway 再校验 Token、scope 和 allowlist。模型只在允许集合中做选择，业务服务仍执行最终权限和参数校验。

### Q025｜AgentCard 的作用是什么？
> [!note] 候选人逐字稿 AgentCard 用来描述 Agent 身份、服务地址、skills、支持的交互方式和认证要求，编排中心根据能力描述筛选候选 Agent。租户策略、灰度状态和内部健康信息属于平台控制面扩展，不能说全部都是 A2A 标准字段。最终路由是 AgentCard 能力信息和平台策略的组合结果。

### Q026｜AgentCard 如何发现、缓存和更新？
> [!note] 候选人逐字稿 实际方案是 **【启动拉取/定时同步/注册中心推送/后台发布】**。编排侧做带 TTL 的缓存，更新前校验 Schema 和兼容性，再切换生效版本；健康检查失败的 Agent 要摘除或降级。这里需要准备真实 Registry、缓存键、TTL 和版本切换流程，不能只回答"从配置中心读取"。

### Q027｜AgentCard 的 Schema 变更如何兼容？
> [!note] 候选人逐字稿 新增可选字段一般可以向后兼容，删除字段、修改类型或语义要发布新版本。调用前使用 Pydantic 校验，编排中心根据自己支持的版本选择 Agent，并为旧版本保留迁移期。若项目当前没有版本并存，我会说明现阶段采用固定版本和发布联调，版本化是后续治理方向。

### Q028｜你如何理解 A2A？
> [!note] 候选人逐字稿 A2A 是 Agent 之间的协作协议，重点是能力发现、任务创建、任务状态、消息和 Artifact 交换，以及长任务的流式更新。它不负责模型训练、RAG 或数据库事务。项目用它把编排中心和业务 Agent 解耦，使新增 Agent 主要增加能力描述、执行器和配置。

### Q029｜A2A、MCP 和 Function Calling 有什么区别？
> [!note] 候选人逐字稿 Function Calling 是模型在推理中选择结构化工具；MCP 更偏向 Agent 或模型连接外部工具、资源和 Prompt；A2A 面向 Agent 与 Agent 的任务协作。我们的编排中心通过 A2A 调业务 Agent，业务 Agent 内部再通过 Tool Gateway 调课程、交易或 RAG 服务。没有真正使用 MCP 的模块不能包装成 MCP Server。

### Q030｜你们使用的是哪个 A2A 版本？
> [!note] 候选人逐字稿 项目固定使用 **【准确 SDK 名称和版本】**，采用 **【JSON-RPC over HTTP/REST 等真实绑定】**，流式结果通过 SSE。A2A 在项目期间迭代较快，所以 AgentCard 路径、字段和状态名称以锁定版本为准。项目是在 **【真实月份】** 开始接入 A2A，此前如果使用内部 HTTP 调用，需要如实说明演进过程。
> [!warning] 风险提示 A2A 协议在 2025 年才公开。不能声称 2024 年已经使用公开 A2A SDK。

### Q031｜A2A Task 与普通 HTTP 请求有什么区别？
> [!note] 候选人逐字稿 Task 有独立 taskId 和生命周期，即使连接断开，任务可以继续执行，调用方可以查询、订阅或取消。一个 contextId 还可以关联多次任务。对短任务可以同步返回，但 RAG、复杂工具链和长推理更适合持久化任务模型。

### Q032｜任务状态机有哪些状态？
> [!note] 候选人逐字稿 外部状态严格以项目采用的 A2A SDK 枚举为准，内部通常映射提交、执行中、等待输入、完成、失败和取消。状态迁移必须受控，例如终态不能回到执行中。面试时我会展示实际状态表和转换条件，而不是混用不同版本文档中的状态名。

### Q033｜Persistent TaskStore 保存哪些字段？
> [!note] 候选人逐字稿 至少包括 taskId、contextId、tenantId、目标 Agent、当前状态、幂等键、请求摘要或引用、结果引用、版本号和时间字段。大文本和 token 流可以拆到事件表、对象存储或 Redis，不全部塞入任务主表。实际数据库、索引和清理策略是 **【待补充】**。

### Q034｜A2A Task 如何保证幂等？
> [!note] 候选人逐字稿 入口以 tenantId 加幂等键建立唯一约束，重复请求且 payload 摘要一致时返回原 taskId，不一致则报冲突。购课等写操作还要把业务幂等键传给交易服务，由业务唯一索引或订单状态机兜底。TaskStore 幂等不能替代业务幂等。

### Q035｜调用超时后为什么不能直接重试？
> [!note] 候选人逐字稿 超时只代表调用方没收到结果，不代表下游没有执行。处理时先用 taskId 查询状态，确认任务未创建或明确失败后再重试；读操作可以更积极，写操作必须依赖业务幂等键。具体超时和次数要按真实配置回答。

### Q036｜任务取消是否等于事务回滚？
> [!note] 候选人逐字稿 不等于。取消是 best effort，Task Guard 标记取消意图并通知执行器停止后续步骤，但已经完成的外部写操作需要业务补偿。面试时不能说取消后所有 Tool 调用都会自动回滚。

### Q037｜Task Guard 是 A2A 官方组件吗？
> [!note] 候选人逐字稿 不是，它是项目内部保护层，用于任务归属校验、状态迁移校验、并发限制、超时和取消检查。简历中应主动说明它是平台自定义模块，避免让面试官误以为是协议标准组件。

### Q038｜Event Bus 用的是什么，如何保证一致性？
> [!note] 候选人逐字稿 实际 Event Bus 是 **【进程内事件/Redis Streams/RabbitMQ/其他】**。任务状态更新与事件发送如果跨存储，会有写库成功但发事件失败的问题；如果采用 Outbox，就说明同事务写事件表和后台投递流程；如果没有，则如实说明依赖重试和状态查询兜底，不能声称严格一致。

### Q039｜AgentExecutor 和 Agent Runtime 的区别是什么？
> [!note] 候选人逐字稿 AgentExecutor 是协议适配层，把 A2A Task 和上下文转换为 Agent 输入，再把结果映射成任务事件；Agent Runtime 负责模型调用、Prompt、Tool 调度和本 Agent 的内部运行规范。这样协议层和业务 Agent 逻辑不会强耦合。类结构为：Client 侧是 A2ACardResolver -> ClientFactory -> JSON-RPC Client；Server 侧是 A2AStarletteApplication -> DefaultRequestHandler -> Persistent TaskStore -> AgentExecutor。

### Q040｜为什么还需要 Tool Gateway？
> [!note] 候选人逐字稿 Agent 不能直接拼 URL、SQL 或任意服务名。Tool Gateway 统一维护工具元数据和参数 Schema，校验 Agent、租户和场景权限，并处理超时、异常码、审计和幂等。真正的业务校验仍由下游服务完成，Prompt 约束不是安全边界。

### Q041｜如何防止 Agent 调用不该调用的 Tool？
> [!note] 候选人逐字稿 根据 tenantId、AgentId 和场景生成服务端 Tool allowlist，模型只看到允许的工具；Tool Gateway 再做权限和参数校验，高风险写操作需要用户确认或业务侧二次校验。还要限制 URL、SQL、价格等敏感参数，不能由模型自由生成。

### Q042｜如何防御 Prompt Injection？
> [!note] 候选人逐字稿 用户输入和 RAG 文档都按不可信数据处理，文档里的指令不能覆盖系统策略。Tool 使用结构化 Schema、最小权限和 allowlist，敏感参数由服务端补全或校验；输出侧做敏感信息和引用检查。已落地的措施包括：每个 Agent 使用独立 Prompt 和 Tool 白名单；Tool 经业务网关调用并携带用户委托 Token，入参使用 Pydantic 或结构化 Schema 校验，读写 Tool 分权，写操作使用业务 requestNo 做幂等；RAG 回答只基于实际召回内容并返回引用，未实现的只能作为改进项。

### Q043｜多租户数据如何隔离？
> [!note] 候选人逐字稿 tenantId 来自可信鉴权上下文，不接受模型或正文指定。TaskStore、Checkpoint、Redis Key、业务查询和向量检索都携带 tenantId，并在数据库或 Milvus 过滤表达式中强制执行。实际采用共享表 tenant_id、独立 schema 还是独立库要如实说明。

### Q044｜服务间鉴权怎么做，会透传用户 JWT 吗？
> [!note] 候选人逐字稿 外部用户 Token 用于入口认证，服务间更适合短时委托凭证或服务身份，只携带必要 Claims，并验证 audience、scope、签名和过期时间。项目实际采用 **【JWT 透传/Delegated Token/mTLS/网关签名】**。如果目前只是 JWT 透传，我会说明现状以及 Token 泄露和权限过大的改进方向。

### Q045｜SSE Event Gateway 有哪些事件类型？
> [!note] 候选人逐字稿 平台会统一为文本增量、Artifact、工具状态或结果、RAG 引用、任务状态、错误、心跳和结束事件。每条事件带 taskId、eventId 或 sequence、eventType 和时间信息。平台自定义前端事件与 A2A 标准事件不是同一套名称，工具结果通常映射成 DataPart、Artifact 或自定义事件，不直接声称 ToolResult 是标准 A2A 事件。

### Q046｜SSE 如何实现断线重连？
> [!note] 候选人逐字稿 服务端给事件分配递增 eventId，并在 Redis 保留一定窗口。客户端重连携带 Last-Event-ID，服务端先回放游标之后的事件，再订阅新事件；缓存过期时只能查询 TaskStore 返回当前或最终状态，不能保证从任意历史 token 无损续传。数据结构、TTL 和窗口是 **【待补充】**。

### Q047｜如何处理 SSE 重复、乱序和慢客户端？
> [!note] 候选人逐字稿 聚合层统一分配 sequence，客户端按 taskId 加 sequence 去重，语义通常是至少一次而不是端到端 exactly-once。连接层发送 heartbeat，关闭代理缓冲，并使用有界队列或慢客户端断开策略，避免单连接拖垮服务。真实参数是 **【待补充】**。

### Q048｜OpenTelemetry 具体做了什么？
> [!note] 候选人逐字稿 入口创建或透传 trace context，在 A2A、Tool、模型和 RAG 调用处建立 span，日志通过 traceId、requestId、taskId 和 contextId 关联。指标关注任务成功率、阶段耗时、超时率、Tool 错误、活跃 SSE 连接和模型 token。Collector 和存储 **【待补充】**；统一看板监控意图路由、Tool 成功率、A2A P95/P99、首 token 时延和失败类型；如果只做日志关联，不应说成完整 OTel 体系。

### Q049｜如何测试多智能体系统？
> [!note] 候选人逐字稿 分四层测试：节点和路由单元测试；A2A Task 生命周期、幂等和版本兼容契约测试；Mock Agent/Tool 的超时、取消和 SSE 重连集成测试；真实业务问题集的路由和 RAG 效果评估。项目覆盖：Service 层单元测试；外部服务 Mock 或沙箱；接口正常、边界、权限和重复请求测试；数据库事务回滚与并发条件更新测试；MQ 重复、乱序、消费失败和重放测试；Agent/RAG 固定评估集与 Badcase 回归，没有完成的测试作为改进项说明。

### Q050｜请讲一个这个项目中的故障排查案例。
> [!note] 候选人逐字稿 **【替换为真实案例】** 例如 SSE 偶发重复时，我先用 traceId 和 taskId 确认下游任务只执行一次，再比对事件 sequence，发现重连回放与实时订阅之间存在重叠窗口。修复方式是在订阅切换点记录最大已发送 sequence，并由客户端按 taskId+sequence 幂等处理。回答要包含现象、假设、证据、根因、修复和复盘，不能只说"查日志解决"。

## 第三部分｜企业知识库 RAG 平台：检索、文档处理与效果评估

### Q051｜请介绍 企业知识库 RAG 平台 项目。
> [!note] 候选人逐字稿 这是面向铁路无线调车灯显设备运维场景的知识问答平台，知识来源包括设备说明书、检修规程、故障码和告警处理手册。系统先做问题分类和查询处理，再通过 BM25、BGE-M3 稀疏与稠密向量进行多路召回，使用 BGE Reranker 精排，最后让模型基于证据生成答案并返回引用。我的职责是 **【真实负责模块】**，重点解决专业术语召回、长文档切片和无依据回答问题。

### Q052｜为什么不能直接把问题发给通义千问？
> [!note] 候选人逐字稿 通用模型可能没有企业私有资料，也无法保证知识版本和出处。铁路运维问题对准确性和可追溯性要求高，所以需要检索权威文档并把证据提供给模型。RAG 仍不能替代现场安全确认，因此系统定位是辅助查询，并设置无证据拒答和引用展示。

### Q053｜请画出在线 RAG 链路。
> [!note] 候选人逐字稿 用户问题进入 RAG API 后，先做意图判断、指代补全或 Query Rewrite，再执行 FAQ/BM25、BGE-M3 sparse 和 dense 多路召回，按权限及 metadata 过滤。候选文档合并去重后进入 BGE Reranker，选取 topN 父块构造上下文，模型基于证据生成答案，最后通过 SSE 返回正文和 source 引用。

### Q054｜离线知识入库链路是什么？
> [!note] 候选人逐字稿 数据源接入后先做文件校验、权限确认、脱敏和去重，再由异步 Worker 完成 PDF、Word、PPT、图片解析和 OCR。正文经过清洗、标题层级恢复、父子分块和 metadata 绑定，生成 Embedding 后写入 Milvus，并记录文档、chunk、索引版本和任务状态。增量更新时先构建新版本，校验通过后切换，避免半成品索引对外服务。

### Q055｜为什么使用父子分块？
> [!note] 候选人逐字稿 小块适合检索，能够提高问题与局部文本的匹配精度；但直接把小块交给模型可能缺少上下文。我们对子块生成向量并召回，再返回对应父块作为生成上下文，兼顾检索粒度和语义完整性。父子关系、章节标题和页码都通过 metadata 保存，便于引用与去重。

### Q056｜为什么父块 1200 token、子块 300 token？
> [!note] 候选人逐字稿 这不是固定最佳值，而是根据文档结构、问题长度、模型上下文和评估结果选择的初始参数。300 token 子块能覆盖多数故障描述和操作步骤，1200 token 父块保留完整章节语义。需要准备真实 overlap、评估样本和对比结果；如果没有做系统实验，应说这是基于样本验证的工程参数，不能声称全局最优。

### Q057｜分块 overlap 设置多少，为什么？
> [!note] 候选人逐字稿 实际设置是**50（默认父块约 1200 字、子块约 300 字）**。overlap 用于避免关键信息被切在边界两侧，但过大会产生重复召回、增加索引和 token 成本。我们会结合标题层级、句子边界和表格边界切分，而不是只按固定长度截断；召回后还要按父块和 source 去重。

### Q058｜BGE-M3 的 dense 和 sparse 分别解决什么问题？
> [!note] 候选人逐字稿 dense 向量擅长语义相似，能够召回表达不同但意思接近的内容；sparse 权重更关注词项匹配，对设备型号、故障码、标准编号等精确关键词更有效。铁路文档同时包含自然语言和大量专业代码，所以两路互补。BGE-M3 还支持多语言和多粒度表示，但项目实际使用的是 dense 与 sparse 两种输出。

### Q059｜BGE-M3 sparse 和 BM25 有什么区别，为什么两者都用？
> [!note] 候选人逐字稿 BM25 是基于词频、逆文档频率和长度归一化的统计检索，解释性强且不依赖模型；BGE-M3 sparse 是学习得到的词项权重，能结合语义训练信息。两者可能存在重叠，所以是否同时保留要通过评估决定。项目实际组合为：FAQ 快速路径使用 BM25；RAG 路径使用 BGE-M3 dense+sparse 混合召回；两路实际召回占比 **【待补充】**，不能只因为技术栈里有两个名词就说都在线使用。

### Q060｜Milvus collection 如何设计？
> [!note] 候选人逐字稿 collection 至少包含主键、tenantId 或知识库 ID、documentId、parentId、chunkId、dense vector、sparse vector、正文或正文引用以及页码、标题、版本等 metadata。查询先用标量过滤限制知识库和权限，再做向量检索。真实维度是 BGE-M3 dense 的 1024，索引类型、metric、分区和副本数是 IVF_FLAT。

### Q061｜Milvus 使用什么索引和距离度量？
> [!note] 候选人逐字稿 需要按真实配置回答，例如 dense 使用 COSINE 或 IP，索引采用 HNSW、IVF_FLAT 等；sparse 使用对应的稀疏索引。选择取决于数据量、召回率、内存和延迟。面试时要能说出构建参数和查询参数，不能只回答"Milvus 默认索引"。

### Q062｜WeightedRanker 的权重怎么定？
> [!note] 候选人逐字稿 权重应该通过标注问题集网格搜索或分场景评估确定，而不是凭感觉。专业型号和故障码问题可以提高 sparse/BM25 权重，描述性问题可以提高 dense 权重。项目实际权重为 dense 1.0、sparse 0.7；是否支持动态配置 **【待补充】**；没有实验记录就不要现场编数值。

### Q063｜为什么召回后还需要 Reranker？
> [!note] 候选人逐字稿 第一阶段向量检索追求召回率，候选中会有语义接近但并不真正回答问题的块。Reranker 以 query-document 对做交叉编码，能更精细地判断相关性，再把更少、更高质量的上下文交给模型。代价是计算开销，因此只对第一阶段 topK 候选执行，并控制 rerank topN。

### Q064｜topK、topN 和阈值如何设置？
> [!note] 候选人逐字稿 通过离线问题集评估 context recall、context precision、答案正确性和延迟后选择。一般先保证多路召回覆盖，再用 reranker 缩小上下文；低于相关性阈值时进入拒答或澄清。第一阶段 topK=5，rerank 后取 2 个父块；相关性阈值和完整调优记录 **【待补充】**，不能用通用数字冒充项目参数。

### Q065｜BERT 问题分类和大模型策略路由是否重复？
> [!note] 候选人逐字稿 可以做成两级路由。BERT 或轻量分类器负责高频、边界清晰的粗分类，延迟和成本低；复杂问题再交给大模型判断直接检索、HyDE 或子查询拆分。若项目实际上只使用其中一种，就按真实情况说明。简历当前同时写了 BERT 和"大模型自主判别"，需要准备清楚两者的调用顺序。

### Q066｜什么是 HyDE，什么时候不适合用？
> [!note] 候选人逐字稿 HyDE 先让模型生成一段假设答案，再用假设答案做检索，适合原问题过短或表达与文档差异较大的情况。风险是模型假设偏离事实，会把检索带向错误方向，并增加一次模型调用。我们只在特定意图或低召回场景使用，不能对所有问题默认开启。

### Q067｜复杂问题如何做子查询拆分？
> [!note] 候选人逐字稿 先用结构化输出生成相互独立、可检索的子问题，并限制数量和类型；各子查询并行召回，合并时按 source、parentId 和相关性去重，最终让模型基于全部证据综合回答。涉及先后步骤的问题还要保留顺序。拆分失败或子问题偏离时回退到原问题检索。

### Q068｜如何实现 Query Rewrite？
> [!note] 候选人逐字稿 Query Rewrite 主要做指代消解、补全设备型号和上下文省略，不改变用户原始意图。Prompt 要输出原始问题、重写问题和关键过滤条件，并做长度与字段校验。为便于排障，检索日志同时保留原 query 与 rewritten query，但敏感数据要脱敏。

### Q069｜如何降低 RAG 幻觉？
> [!note] 候选人逐字稿 不能承诺消除幻觉。我们从检索、生成和输出三层控制：提高证据召回与精排质量；Prompt 要求只能基于上下文并在证据不足时拒答；输出附带 source、页码和片段，并检查引用是否真的支持结论。高风险运维问题还要展示"辅助查询，不替代现场规章判断"。

### Q070｜无依据拒答如何判断？
> [!note] 候选人逐字稿 不能只靠模型自己说"没有依据"。可以结合 reranker 分数、有效证据数量、来源权限和答案引用覆盖率判断；低于阈值时返回固定兜底或要求补充设备型号。阈值需要用已知可答和不可答问题集共同校准，避免过度拒答或错误自信。

### Q071｜引用溯源如何实现？
> [!note] 候选人逐字稿 每个 chunk 保存 documentId、文件名、页码、章节、parentId 和版本。生成上下文时给证据分配稳定编号，要求模型在结论后引用编号；返回后再校验引用编号存在且文本相关。前端展示文件、页码和命中片段，不能只显示模型生成的虚假来源名称。

### Q072｜PDF、Word、PPT 和图片分别如何解析？
> [!note] 候选人逐字稿 PDF 文本优先用 PyMuPDF 提取，扫描件和图片使用 PP-Structure 或实际 OCR 服务；Word、PPT 使用对应结构化解析库并保留标题、表格和页码信息。解析后统一成内部 Document 模型。需要准备复杂表格、页眉页脚、乱码和空页的处理方式，以及失败文件如何人工重试。

### Q073｜表格怎么处理，直接转纯文本吗？
> [!note] 候选人逐字稿 简单表格可以按行列转 Markdown 或结构化文本，同时保存表名和上下文；跨页表格、合并单元格和设备参数表需要专门规则，不能完全依赖普通段落抽取。检索时可以把整表作为父块、行记录作为子块，并在生成时返回原表位置。实际支持范围要如实说明。

### Q074｜文档更新、删除和索引回滚怎么做？
> [!note] 候选人逐字稿 用 documentId 和 version 管理文档版本，入库任务先构建新 chunk 和新索引版本，完成校验后再切换可见版本。删除采用逻辑删除加异步清理，查询时过滤失效版本；失败时保留旧版本继续服务。需要防止 MySQL 元数据成功但 Milvus 写入不完整，可用任务状态和补偿扫描处理。

### Q075｜RAG 权限过滤在哪一层做？
> [!note] 候选人逐字稿 用户可访问的知识库列表由可信业务权限服务给出，检索时在 Milvus 标量过滤或分区中强制限制 tenantId、knowledgeBaseId 和文档权限。不能先检索全库再只在前端隐藏，因为候选内容已经可能进入模型上下文。缓存键也必须包含租户和权限版本。

### Q076｜RAGAS 的四个指标分别是什么？
> [!note] 候选人逐字稿 faithfulness 评估答案是否得到上下文支持；answer relevancy 评估答案是否回应问题；context precision 评估检索上下文中相关内容的排序和比例；context recall 评估应有证据是否被召回。自动指标需要抽样人工复核，尤其专业领域不能只相信另一个模型打分。项目实际评估集、评估模型和结果是上下文相关性，上下文召回率，忠实度，答案相关性。

### Q077｜如何优化端到端延迟和成本？
> [!note] 候选人逐字稿 先分解耗时：查询改写、Embedding、Milvus、reranker、模型首 token 和总生成时间。可并行执行多路召回，缓存高频 query/embedding，控制 topK 与上下文长度，对 FAQ 走快速路径，并为复杂策略设置预算。优化前后要看 P95、首 token、token 消耗和答案质量，不能只追求速度。

### Q078｜为什么一个项目用 Milvus，另一个项目用 pgvector？
> [!note] 候选人逐字稿 pgvector 与 PostgreSQL 集成简单，适合数据规模较小、事务和元数据查询较多的仓储知识库；Milvus 更适合独立向量服务、大规模检索和 dense/sparse 混合能力。选择取决于数据量、运维成本和检索需求，不代表 Milvus 在所有场景都更好。

## 第四部分｜鲜享生活与业务系统：Spring AI、仓储和设计模式

### Q079｜请介绍鲜享生活与业务系统项目以及你的职责。
> [!note] 候选人逐字稿 这是面向多货主企业的 SaaS 仓储平台，覆盖入库、上架、库存、波次拣货、任务执行和 IoT 设备监控。我在传统 WMS 业务之外参与了库存智能问答，使用 Spring AI 和 DashScope 让模型通过受控工具查询库存、货主、仓库和商品信息；同时负责 **【真实业务模块：ASN/波次/任务表】**。个人职责和团队边界是 **【待补充】**。

### Q080｜Spring AI 的 Function Calling 完整流程是什么？
> [!note] 候选人逐字稿 后端先根据用户和租户上下文构造允许的工具列表与 JSON Schema，模型返回工具名和结构化参数；服务端进行权限、类型、范围和业务校验后调用 Java 方法，再把结果作为 tool result 交给模型生成最终回答。模型没有数据库账号，也不能自行拼 SQL。调用次数、超时和循环次数要有上限。

### Q081｜四个工具如何设计，为什么不做一个万能查询工具？
> [!note] 候选人逐字稿 工具按库存、货主、仓库和商品边界拆分，每个工具有明确参数和最小返回字段。万能工具容易出现参数歧义、权限过大、提示词难选择以及任意查询风险。多个工具之间如果需要组合，由 Agent 做有限步骤编排，但写操作和高风险查询不开放给通用问答 Agent。

### Q082｜如何防止模型越权查询其他租户库存？
> [!note] 候选人逐字稿 tenantId 和 userId 由后端鉴权上下文注入，不允许模型参数覆盖。工具方法内部按租户、仓库权限和数据范围查询，并对商品、货主等 ID 做归属校验。日志和缓存同样按租户隔离，模型只接收最小必要结果。

### Q083｜工具参数解析失败怎么办？
> [!note] 候选人逐字稿 先使用 Schema 和 Bean Validation 校验，缺少可澄清的信息时让模型向用户追问；类型错误或越界参数返回结构化错误，允许模型在限定次数内修正。连续失败后终止 Tool 循环并返回明确提示，不能无限调用。实际最大轮数和错误码是 **【待补充】**。

### Q084｜Redis 会话记忆如何设计？
> [!note] 候选人逐字稿 Key 至少包含 tenantId、userId 和 sessionId，Value 保存最近消息、摘要或结构化上下文，设置 TTL 和最大长度。敏感数据要脱敏，不能无限追加完整对话。服务重启后 Redis 数据仍在，但这只代表外部化会话状态，不代表永久存储；过期和用户主动清除要有策略。

### Q085｜简历中的"思考过程处理"具体是什么？
> [!note] 候选人逐字稿 我们没有向前端展示模型原始思维链，展示的是可解释的阶段状态，例如"正在识别意图""正在查询库存""正在生成回答"，以及工具调用摘要。原始隐藏推理不存储、不返回。简历建议改成"SSE 流式输出与生成阶段状态处理"。

### Q086｜WMS RAG 为什么选择 pgvector？
> [!note] 候选人逐字稿 仓储知识库规模相对可控，业务元数据本来就在 PostgreSQL，pgvector 可以减少独立向量组件和运维成本，并方便用 SQL 做租户和文档过滤。若后续数据量或混合检索需求显著增长，可以评估独立 Milvus。文档量、索引和距离度量 **【待补充】**；检索阈值为 0.5，topK=2。

### Q087｜ASN 入库流程是什么？
> [!note] 候选人逐字稿 ASN 创建后进入待收货，PDA 扫描商品条码匹配入库单并录入批次、生产日期和保质期；系统校验数量、商品与库区规则，收货完成后生成上架任务并分配执行人。不良品进入隔离区，不进入可售库存。状态机、事务边界和异常回退要按真实实现说明。

### Q088｜"批次号+商品ID+储位"唯一索引是否足够？
> [!note] 候选人逐字稿 是否足够取决于租户、货主、仓库和库存状态模型。多租户系统通常还需要 tenantId、ownerId、warehouseId 等维度，否则不同租户可能冲突。面试时应给出真实唯一键，并说明批次为空、效期变更、质量状态和单位换算如何处理。

### Q089｜波次拣货为什么使用策略模式和责任链？
> [!note] 候选人逐字稿 策略模式封装单品单件、一品多件等不同选单算法，责任链按优先级尝试策略并决定是否继续。这样新增策略只增加实现类和配置，不修改主流程。需要说明订单是否只能进入一个波次、并发抢单如何防重，以及策略失败后的兜底。

### Q090｜统一任务表如何设计？
> [!note] 候选人逐字稿 任务主表保存 taskType、businessId、assignee、status、version 和时间信息，执行记录表保存每次领取、开始、完成、失败和操作人。execute 模板方法统一做状态校验、CAS 更新、日志和后续任务生成。通用表减少重复，但各任务差异字段应放扩展表或 JSON，并避免演变成难维护的大宽表。

### Q091｜CAS 如何防止任务被重复执行？
> [!note] 候选人逐字稿 更新时使用 where id=? and status=? and version=?，只有一个执行者能把待领取改为执行中；受影响行数为 0 的请求说明状态已变化，返回冲突。CAS 只保护单条状态迁移，涉及库存和多个任务时仍需要事务、唯一约束或分布式协调。

### Q092｜使用 JeecgBoot 低代码平台有什么优缺点？
> [!note] 候选人逐字稿 优点是通用 CRUD、权限、字典和后台页面交付快，适合标准管理功能；缺点是复杂领域逻辑容易被生成代码和框架约束，升级也可能产生兼容问题。我们把核心库存、任务和波次逻辑放在独立领域服务，低代码主要承载配置和管理页面。实际缩短的交付时间只有存在真实记录时才给数字。

## 第五部分｜Java 微服务、电商与供应链

### Q093｜请介绍悦享生活商城项目。
> [!note] 候选人逐字稿 这是品牌自营 B2C 商城，按网关、用户、商品、搜索、购物车、交易和支付拆分微服务。我主要参与 **【真实模块】**，重点做订单、库存和支付链路。下单阶段通过业务幂等、库存条件更新和事务策略避免重复下单与超卖；支付结果通过 RabbitMQ、消费幂等和补偿任务实现可靠通知。

### Q094｜一次下单的完整流程是什么？
> [!note] 候选人逐字稿 网关完成身份认证后，交易服务校验购物车、商品状态和价格，生成订单及明细，并携带业务幂等键请求库存扣减或预占。成功后清理购物车并返回待支付订单；支付完成后异步更新订单状态并触发后续履约。价格、优惠和库存必须以服务端快照或实时校验结果为准，不能信任前端参数。

### Q095｜如何防止重复下单？
> [!note] 候选人逐字稿 前端请求携带一次性令牌或业务幂等键，服务端以用户、场景和幂等键建立唯一约束。重复请求如果参数一致则返回原订单，不一致则报冲突。数据库唯一索引是最终防线，Redis 只用于快速拦截，不能替代持久化约束。

### Q096｜如何防止库存超卖？
> [!note] 候选人逐字稿 核心是数据库条件更新，例如 update stock set available=available-? where sku_id=? and available>=?，根据受影响行数判断是否成功。高并发场景还可以先预占再确认扣减，并为订单和库存事件设置幂等。分布式锁不是唯一方案，也不能替代库存表的原子条件。

### Q097｜Seata AT 的原理是什么？
> [!note] 候选人逐字稿 AT 模式由 TC 协调全局事务，TM 发起和提交或回滚全局事务，RM 管理分支事务。第一阶段本地事务提交业务数据和 undo_log，第二阶段全局提交时异步清理，回滚时根据前后镜像生成补偿 SQL。它使用全局锁处理写冲突，适合关系数据库，但长事务、高并发热点和复杂 SQL 会带来性能与兼容性问题。

### Q098｜既用了 Seata，为什么还要库存条件更新和幂等？
> [!note] 候选人逐字稿 Seata 解决跨服务事务协调，但不能代替业务并发控制和重复请求防护。库存条件更新保证数量不会变成负数，幂等保证重试不会重复下单；Seata 负责部分跨服务失败时的整体回滚。三者解决的问题不同。实际项目哪些服务纳入全局事务要按真实边界说明。

### Q099｜为什么支付通知使用本地消息表？
> [!note] 候选人逐字稿 需要保证支付状态落库和待发送事件不会只成功一个。把支付状态和消息记录放在同一本地事务，后台任务扫描未发送消息并投递 MQ，收到 broker confirm 后更新状态；失败继续重试。消费者仍需幂等，因为消息可能重复投递。本地消息表实现的是最终一致性，不是全局 exactly-once。

### Q100｜RabbitMQ 如何保证消息不丢？
> [!note] 候选人逐字稿 生产端使用持久化交换机、队列和消息，并处理 publisher confirm；业务侧用 Outbox 或补偿扫描避免数据库提交后未发送。消费端手动 ack，处理成功再确认，失败按次数重试并进入死信队列或人工补偿。还要监控堆积、死信和消费延迟。

### Q101｜如何处理重复消费？
> [!note] 候选人逐字稿 以业务唯一键或 messageId 建消费幂等表或唯一索引，消费前或事务内检查是否处理。状态机也要限制重复迁移，例如已支付订单再次收到支付成功事件只返回成功，不重复扣库存。不能依赖 RabbitMQ 绝对不重复。

### Q102｜如何保证消息顺序？
> [!note] 候选人逐字稿 先判断业务是否真的需要全局顺序，通常只要求同一订单内有序。可以按订单 ID 路由到同一队列或同一消费分区，并让单一消费者顺序处理；同时使用状态机拒绝非法逆序事件。重试和死信会打乱顺序，所以必须以业务状态校验兜底。

### Q103｜Redis 如何处理缓存穿透、击穿和雪崩？
> [!note] 候选人逐字稿 穿透可以用参数校验、空值缓存和布隆过滤器；击穿针对热点 Key 使用互斥重建、逻辑过期或提前刷新；雪崩通过随机过期、分批预热、限流降级和高可用部署降低风险。不能把所有问题都用分布式锁解决，缓存更新还要考虑数据库与缓存一致性。

### Q104｜Redisson 分布式锁有哪些坑？
> [!note] 候选人逐字稿 必须明确锁粒度、等待时间、租约、可重入和异常释放。看门狗只能在客户端存活时续期，网络分区或长时间 STW 仍可能导致锁失效；锁也不能替代数据库唯一约束。解锁时必须确认锁属于当前线程，业务操作最好再有幂等和状态检查。

### Q105｜商品缓存如何与数据库保持一致？
> [!note] 候选人逐字稿 常用 Cache Aside：读缓存未命中查库并回填，写操作先更新数据库再删除缓存。删除失败要通过重试或消息补偿，热点 Key 可以延迟双删但仍不是强一致保证。对价格和库存等关键数据，最终决策以业务服务和数据库校验为准。

### Q106｜Elasticsearch 索引如何同步？
> [!note] 候选人逐字稿 数据库事务完成后产生变更事件，由 MQ 消费者按业务主键做幂等 upsert；失败进入重试和死信，定时对账扫描数据库与索引差异。搜索索引是派生数据，可以重建。更新顺序要带版本号或更新时间，防止旧消息覆盖新数据。

### Q107｜Sentinel 做了哪些保护？
> [!note] 候选人逐字稿 对登录、搜索和下单按 QPS、并发线程或热点参数设置规则，外部依赖配置熔断，非核心查询提供降级响应。规则可以从配置中心动态下发，但阈值要基于容量测试和监控，不是拍脑袋设置。下单接口被限流时要明确返回和客户端重试策略。

### Q108｜请介绍采供云项目。
> [!note] 候选人逐字稿 这是制造企业、供应商和采购部门之间的 B2B 协同平台，覆盖供应商准入、询报价、采购订单、收货、库存、对账和发票。我主要负责 **【真实模块】**，重点处理采购订单状态机、库存预占最终一致性、组织数据权限和批量对账任务。

### Q109｜采购订单的状态机如何设计？
> [!note] 候选人逐字稿 状态包括 **【按真实枚举填写】**，每个命令只允许从指定旧状态迁移到新状态。更新 SQL 带旧状态和 version 做 CAS，受影响行数为 0 表示并发冲突。审批、取消和收货还要检查角色、数量及下游状态，不能只修改一个 status 字段。

### Q110｜库存预占最终一致性如何实现？
> [!note] 候选人逐字稿 订单审批与 Outbox 事件在同一本地事务提交，投递库存预占消息；库存服务以订单行或 reservationId 做幂等，预占成功或失败后回传结果，订单服务再推进状态。超时任务定期查询和补偿。若预占成功但订单最终取消，需要发送释放事件，不能依赖数据库回滚跨服务撤销。

### Q111｜本地消息表会无限增长吗？
> [!note] 候选人逐字稿 要按状态和时间建立索引，发送成功的数据按保留策略归档或分区清理；失败消息限制重试次数并转人工或死信。扫描任务使用分页、抢占或 SKIP LOCKED，避免多实例重复处理。消息表不是把所有 payload 永久保存，而是可靠投递的过渡记录。

### Q112｜多组织数据权限如何实现？
> [!note] 候选人逐字稿 用户登录后生成可信的租户、组织和角色上下文，服务端根据数据范围生成允许的组织 ID 集合，再通过 MyBatis 拦截器或显式查询条件注入。复杂 SQL、子查询和批量导出必须测试，不能只靠前端传 organizationId。超级管理员和跨组织岗位要有明确授权与审计。

### Q113｜MyBatis 数据权限拦截器有什么风险？
> [!note] 候选人逐字稿 SQL 解析可能不支持部分方言、Union、子查询或自定义函数，错误注入可能造成越权或性能问题。对无法可靠解析的 SQL 应拒绝执行或要求显式权限条件，并用集成测试覆盖。还要防止重复注入和参数数量过大。

### Q114｜对账结算任务如何避免重复生成？
> [!note] 候选人逐字稿 以结算周期、供应商或业务单据建立唯一键，任务创建使用唯一约束和状态校验。XXL-JOB 多实例执行时采用分片、数据库抢占或分布式锁；生成明细和更新任务状态放在合理事务中。失败可从检查点重跑，但每条应付明细必须幂等。

### Q115｜布隆过滤器有什么缺点？
> [!note] 候选人逐字稿 它可能误判存在但不会误判不存在，不能删除或删除成本高，数据更新还要同步。它只能挡住明显不存在的请求，命中后仍需查缓存或数据库。容量和误判率决定位数组和哈希数量，重建期间要有降级方案。

### Q116｜逻辑过期如何处理热点 Key？
> [!note] 候选人逐字稿 Value 中保存逻辑过期时间，读到过期数据时先返回旧值保证低延迟，再由一个线程或分布式锁异步重建。这样牺牲短时间一致性换可用性，不适合价格、库存等必须实时准确的数据。重建失败要监控并限制旧值最大存活时间。

### Q117｜如何排查慢 SQL？
> [!note] 候选人逐字稿 先从监控和慢日志定位 SQL、调用链和数据量，再使用 EXPLAIN/EXPLAIN ANALYZE 查看访问类型、估算行数、索引、回表、临时表和排序。根据查询模式调整联合索引顺序、减少无用列、改写分页或拆分查询，并用真实数据回归 P95。不能只看到全表扫描就盲目加索引。

### Q118｜MySQL 的事务隔离和 MVCC 如何理解？
> [!note] 候选人逐字稿 InnoDB 通过 undo log 和 Read View 提供一致性读，RC 每次一致性读创建新视图，RR 通常在事务内复用视图。当前读使用锁并可能产生 next-key lock 防止幻读。项目中要保持事务短小，避免在事务内调用长耗时远程接口。

### Q119｜Spring 事务有哪些常见失效场景？
> [!note] 候选人逐字稿 同类自调用绕过代理、方法非 public、异常被吞掉、抛出未配置回滚的受检异常、对象不是 Spring Bean、跨线程或跨服务都会导致预期事务不生效。还要注意传播行为和多数据源事务管理器。排查时看代理对象、事务日志和实际连接。

### Q120｜OpenFeign 调用失败如何处理？
> [!note] 候选人逐字稿 配置连接和读取超时，区分可重试的查询与不可盲重试的写请求；结合 Resilience4j 或 Sentinel 做隔离、熔断和降级。写操作使用幂等键并查询状态，不能因读取超时就重复提交。接口还要透传 trace 和必要身份信息，但避免把内部异常直接暴露给用户。

### Q121｜什么时候选择 Seata，什么时候选择最终一致性？
> [!note] 候选人逐字稿 强一致、链路短、数据库兼容且并发可控时可以评估 Seata；长流程、跨异构系统或允许短暂不一致时更适合本地事务加可靠消息和补偿。订单创建和库存预占常用最终一致性，支付和履约也通常采用状态机与事件。选择要基于业务一致性要求，而不是统一技术偏好。

### Q122｜如何划分微服务边界？
> [!note] 候选人逐字稿 依据业务能力、数据所有权、变化频率和团队边界划分，不按数据库表机械拆分。一个服务应拥有自己的核心数据和状态机，跨服务通过明确契约协作。拆得过细会放大网络、事务和运维成本，所以早期可以保持粗粒度，再根据独立扩容和发布需求演进。

## 第六部分｜AI 应用通用工程与系统设计

### Q123｜FastAPI 的 async 有什么价值？
> [!note] 候选人逐字稿 模型、数据库和下游 HTTP 调用以 I/O 等待为主，async 可以在等待期间处理其他请求，提高单进程并发。但如果在 async 路由中调用同步阻塞 SDK，会阻塞事件循环，需要使用异步客户端或线程池。CPU 密集的 OCR、Embedding 或 reranker 应放到独立进程或任务队列。

### Q124｜Python GIL 会影响这个项目吗？
> [!note] 候选人逐字稿 GIL 主要限制同一解释器进程内 CPU 密集 Python 线程并行，对网络 I/O 的 async 并发影响较小。OCR、分词或本地模型推理属于 CPU/GPU 密集任务，应使用多进程、独立 Worker 或推理服务。部署时通过多个 Uvicorn/Gunicorn worker 利用多核，但要注意内存和连接数。

### Q125｜为什么使用 SSE 而不是 WebSocket？
> [!note] 候选人逐字稿 这个场景主要是服务端持续向浏览器推文本和任务事件，SSE 基于 HTTP、浏览器原生支持重连、经过网关和代理更简单。WebSocket 适合高频双向实时通信。用户输入仍走普通 POST，输出走 SSE，可以让协议和鉴权更清晰；如果需要实时打断和双向协作，再评估 WebSocket。

### Q126｜模型结构化输出失败怎么办？
> [!note] 候选人逐字稿 使用明确 JSON Schema 或 Pydantic 模型，服务端解析后做类型、枚举和业务校验。解析失败允许有限次数的修复提示，仍失败则走默认路由或澄清，而不是直接执行工具。对于高风险动作，即使结构合法也要权限和业务二次确认。

### Q127｜如何管理上下文长度？
> [!note] 候选人逐字稿 保留最近窗口，较早对话生成摘要，业务事实结构化保存，需要时按相关性召回。工具结果只保留必要字段，大文档存引用而不是整段反复塞入 Prompt。每次调用计算 token 预算，优先为系统规则、当前问题和证据留空间，并防止摘要不断漂移。

### Q128｜Prompt 如何版本管理和测试？
> [!note] 候选人逐字稿 Prompt 放在配置或代码仓库中，记录版本、模型、参数、变更人和适用场景；发布前用固定评估集比较路由准确率、工具成功率、RAG 质量和安全用例。线上按版本记录日志并支持灰度与回滚。不能只凭几个手工问题判断 Prompt 更好。

### Q129｜模型超时或不可用时怎么降级？
> [!note] 候选人逐字稿 设置连接、首 token 和总超时，限制重试并使用熔断。根据场景可以切换兼容模型、走 FAQ/规则路径、返回任务稍后查询或明确提示稍后重试；写操作不能因为换模型而绕过确认。降级结果要标记并监控，避免静默输出低质量答案。

### Q130｜如何控制 token 成本？
> [!note] 候选人逐字稿 先按模型、Agent、租户和场景记录输入输出 token。通过 Prompt 精简、对话摘要、证据去重、工具返回裁剪、FAQ 快速路径、小模型路由和缓存降低成本。成本优化必须同时看任务成功率和答案质量，不能只压缩 token。

### Q131｜如何选择模型？
> [!note] 候选人逐字稿 根据任务能力、结构化输出稳定性、上下文、延迟、成本、数据合规和供应商可用性评估。意图分类和改写可使用更快模型，复杂生成使用能力更强模型；工具写操作更关注结构化输出和稳定性。最终通过业务评估集和故障测试选择，不凭榜单决定。

### Q132｜如何评估 Agent 系统，而不仅是单次答案？
> [!note] 候选人逐字稿 除答案正确性外，还要评估意图路由、工具选择、参数正确率、任务完成率、平均步骤数、超时率、安全违规率和成本。离线用固定轨迹和 Mock Tool 做回归，线上按场景抽样人工复核。对写操作重点验证是否正确拒绝、澄清和幂等。

### Q133｜请设计一个高并发 Agent 服务。
> [!note] 候选人逐字稿 入口网关做鉴权、限流和请求大小控制，编排服务无状态水平扩容，把会话、Task 和事件状态外置到 PostgreSQL/Redis。长任务异步化并通过 TaskStore 和事件总线解耦，模型、Tool、RAG 分别设置并发舱壁和超时；SSE 使用有界连接与心跳。全链路记录 trace、阶段耗时和 token，并准备降级、重放和容量测试。

### Q134｜模型响应越来越慢，你如何排查？
> [!note] 候选人逐字稿 先按 trace 分解 DNS/连接、排队、首 token、生成、Tool 和 RAG 耗时，确认是供应商、上下文变长、连接池还是下游拥塞。再检查 Prompt token、并发限制、重试放大和代理缓冲。优化后对比 P50/P95、首 token、错误率和质量，不能只看平均值。

### Q135｜你如何设计监控和告警？

## 新增补充｜AI 应用工程师高频深挖知识点

### Q｜RAG 为什么需要混合检索？
> [!note] 候选人逐字稿 单纯向量检索擅长理解语义，但对于产品编号、错误码、专业名词等精确匹配场景效果有限；BM25关键词检索擅长精确匹配，但无法理解语义。因此实际企业知识库通常采用 Dense + Sparse 的混合召回方式，再通过 reranker 模型进行精排。
>
> 在智询通项目中，我采用 BGE-M3 进行多语言向量化，结合 Milvus 做向量召回，同时通过 BM25 做关键词召回，最后融合排序，提高垂直领域问答准确率。

### Q｜Agent 和普通工作流有什么区别？
> [!note] 候选人逐字稿 工作流更多是固定流程编排，节点和执行顺序提前定义；Agent 的核心是让模型根据目标动态选择工具、规划下一步动作。
>
> 实际工程中并不是完全让模型自由决策，而是在 Agent 框架中增加工具约束、权限控制、状态管理和异常兜底，保证智能性和稳定性的平衡。

### Q｜Function Calling 如何保证安全？
> [!note] 候选人逐字稿 Function Calling 本质是让模型生成结构化参数，然后由业务系统执行真实操作，因此不能直接信任模型输出。
>
> 实际设计中需要增加参数校验、权限校验、工具白名单、调用审计以及敏感操作二次确认，避免模型幻觉导致非法业务调用。

### Q｜AI 应用如何做性能优化？
> [!note] 候选人逐字稿 AI 应用性能优化主要分几个方向：
>
> 第一是减少模型调用，例如缓存 Embedding 结果、缓存高频问答；
>
> 第二是优化检索链路，例如合理分块、混合召回、reranker 精排；
>
> 第三是优化服务架构，例如 SSE 流式输出降低首Token等待，RabbitMQ 异步处理长任务，Sentinel 做流量保护。
