## 1. 多线程有几种模型。
**操作系统底层**、**Java JVM**、以及**业务并发设计**三个角度
操作系统底层：用户线程与内核线程，有一对一，一对多，多对多。java采用的是一对一，所以线程开销大，必须使用线程池。
JVM：最核心最常用的就是线程池模型，有工具executors，但资源消耗大，不建议使用。根据阿里巴巴开发规范，要手动创建线程池，有7大参数（核心线程数，最大线程数，存活时间，时间单位，线程工厂，等待队列，拒绝策略）
业务并发：
1. 生产者-消费者模型：能解耦削峰。底层依赖`BlockingQueue`，分布式借助Rabbitmq/kafka。典型场景是订单支付成功后的消息通知，库存扣减，积分发放

2. 主从分治|集合模型：任务拆解执行，最后合并结果。典型场景是首页数据面板。
## 2. 多线程的 volatile 关键字。
volatile 是 JVM 提供的轻量级同步机制，它保证可见性和有序性，但不保证原子性。
`volatile` 关键字通过限制指令重排序，来保证多线程环境下程序执行的有序性
## 3. spring AI它的底层是怎么驱动的
Spring AI 本身不实现 AI 模型，它是一套**统一的抽象层 + 适配器**，底层通过 **Spring Boot 自动装配** 和 **反应式 HTTP 客户端** 驱动各大模型厂商的 REST API，并用 **Advisor 链** 和 **可插拔的向量存储** 实现记忆、RAG 等高级能力。它把 AI 调用变成了一个普通的 Spring Bean 注入。

**1. 接口抽象与动态适配（核心设计）**
- Spring AI 定义了与厂商无关的核心接口：`ChatModel`、`EmbeddingModel`、`ImageModel`、`VectorStore`。
- 每个厂商提供一个 Starter，内部实现这些接口，例如 `OpenAiChatModel` 包装了 OpenAI 的 API。
- 我们编码只依赖接口，切换模型只需换 Starter 和配置，符合**依赖倒置原则**。
**2. 自动配置驱动（Spring Boot 集成）**
- 通过 `spring-ai-xxx-spring-boot-starter` 引入，利用 Spring Boot 的 `AutoConfiguration` 机制，读取 `application.yml` 中的 `api-key`、`base-url` 等配置，自动创建 `OpenAiApi`（底层 HTTP 客户端）和对应的 Model Bean。
- 最终以接口类型 `ChatModel` 注入到容器，实现**零代码**集成。
**3. HTTP 通信与流式驱动（底层通信）**
- 底层默认用 Spring 的 **`WebClient`**（反应式）或 `RestClient` 发送 REST 请求。
- 对于流式对话，使用 **SSE（Server-Sent Events）**，`WebClient` 以流的方式持续接收 token，再通过 **Reactor 的 `Flux<String>`** 逐条推送给上层，实现打字机效果。非流式则直接反序列化 JSON。
- 整个调用本质是：**构建符合厂商 API 格式的请求体 → 发 HTTP 请求 → 解析响应**。
**4. 记忆与 RAG 的切面驱动（高级能力）**
- **记忆**：通过 `Advisor` 链实现，类似 Spring AOP 的拦截器。`MessageChatMemoryAdvisor` 调用前从 `ChatMemory` 取出历史消息拼入 Prompt，调用后更新记忆，让无状态模型变成有状态会话。
- **RAG 检索增强**：底层驱动一个 ETL 管道：读取文档 → 分块 → 调用 `EmbeddingModel` 向量化 → 写入 `VectorStore`。查询时先向量检索，把相关内容注入 Prompt，再调用 `ChatModel` 生成最终回复。这整个过程通过接口解耦，各环节可灵活替换。
## 4. 稀疏向量和那个稠密向量，它的权重，你这个权重是怎么定的
稀疏向量（关键词匹配）**和**稠密向量（语义匹配）。
权重的确定没有银弹，它本质上是一个超参数。
我们通常先根据场景设定一个经验值，再通过离线的召回率评测或在线 A/B 测试迭代到一个最优值。
用户分流：指标有采纳率和追问率。我们设置了答案的拉踩功能，也会对用户追问进行语义判断是否满足要求。
## 5. 数据哪来的
数据库的文档来自企业内部，评测数据集我们采用了一些专家给出的黄金问题，也借助大模型自动合成问题后人工审核。
## 6. 数据的维度怎么处理的。
**统一 Document 抽象 + 元数据标记 + 检索时过滤**：读取阶段用不同加载器和分割器将各类文件转为标准 Document 并打上来源标签，后续分块、向量化完全统一；查询时通过元数据过滤实现业务维度隔离，避免跨领域答案污染。

## 8. 评估体系
主要基于忠实度，答案相关性，上下文召回率和上下文相关性四个指标来判断。
我们搭建了三层评估系统
    1. 第一层检索评估：构建标注的测试集，使用ReCall@5和MMR来确定分块策略和混合检索的权重，找到最优参数。
    2. 第二层生成评估：引入开源自动化评估框架RagAs，主要基于忠实度，答案相关性，上下文召回率和上下文相关性四个指标来判断。
    3. 第三层业务评估：借助设置的回答拉踩数据，和一些人工抽检来兜底。
