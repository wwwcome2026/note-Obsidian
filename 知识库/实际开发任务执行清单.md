# 实际开发任务执行清单

> 用途：入职后处理 Java 后端任务时，按阶段对照。下面是通用工作清单，按公司现有流程和任务风险裁剪；无需每次小改动都做成大型项目。
>
> 完整解释、工具选型、代码与命令示例见同目录《Java后端实际开发全流程指南》。先跑通一个完整任务，再逐步扩大职责喵。

## 一、领到任务

- [ ] 找到关联需求、原型、接口说明和直接负责人。
- [ ] 用自己的话说明：谁，在什么条件下，完成什么动作，看到什么结果。
- [ ] 明确本期范围、不包含的范围、历史数据与旧版本影响。
- [ ] 确认权限、状态、时间、金额、重复、并发和外部失败的规则。
- [ ] 知道怎样验收、由谁验收；未知问题有负责人和确认时间。
- [ ] 在任务卡更新负责人、计划、依赖与阻塞，不只口头接单。

**开始实现前应该拿得出的材料：**任务理解、验收条件、影响范围、依赖清单。

## 二、定位代码与准备环境

- [ ] 确认项目的 JDK、构建工具、框架和依赖版本。
- [ ] 基线能构建、启动，已有关键接口可以调用。
- [ ] 确认当前 profile、数据库、缓存、MQ、存储和第三方环境。
- [ ] 准备隔离测试数据，知道定时任务或消息消费者是否会干扰别人。
- [ ] 从页面请求追到 Controller、Service、Mapper/Repository、SQL 与外部调用。
- [ ] 找到同模块已有实现和相关评审，沿用团队规范。
- [ ] 创建正确基线的工作分支，保留不属于自己的现有改动。

**证据：**可复现启动方式、调用链、表与模块清单、当前分支和基线状态。

## 三、设计和实现

- [ ] 确定接口请求、返回、异常码、权限和异步结果查询方式。
- [ ] 确定状态迁移，处理取消与支付、发货等竞争入口。
- [ ] 确定表、约束、索引和数据库迁移，考虑新旧程序并存。
- [ ] 划清本地事务与远程调用；关键副作用使用可靠任务或事件推进。
- [ ] 重复请求、并发请求、消息重复与超时后结果未知都有处理方案。
- [ ] 写清日志、审计、指标和失败后的补偿或人工处理入口。
- [ ] 生成代码或 AI 辅助代码逐项检查，理解最终差异。
- [ ] 复杂、高风险方案先做必要评审，关键决定回写文档。

**证据：**可审阅方案、代码、迁移、配置模板、测试和接口文档。

## 四、自测和联调

- [ ] 正常、非法参数、无权限、越权、状态拒绝都验证过。
- [ ] 需要幂等与并发控制的业务，核对最终数据和副作用次数。
- [ ] 涉及退款等外部动作，验证超时、重复回调、乱序和补查。
- [ ] 对 SQL、约束和事务，使用适合的真实数据库集成验证。
- [ ] 前后端使用同一接口契约、环境、账号和测试数据。
- [ ] Mock 之外，关键第三方协议有真实对接验证或明确验证安排。
- [ ] 异步流程验证到终态，不能只看 HTTP 200 或“受理成功”。
- [ ] 根据改动风险补性能、安全、兼容和回归验证。

**证据：**测试报告、自测记录、联调结果、尚未验证项及原因。

## 五、提交和代码评审

- [ ] 检查全部差异及暂存区，没有秘密、无关文件和漏提交文件。
- [ ] 提交说明关联任务，并描述业务变化。
- [ ] 推送正确分支，创建 PR / MR，写清范围、验证和发布影响。
- [ ] 必需检查通过，确认实际运行了哪些测试。
- [ ] 理解并处理评审意见，争议用事实、测试或设计约束讨论。
- [ ] 冲突解决后重新验证受影响行为。
- [ ] 按权限与规则合并，确认合并结果及最终候选版本。

**要分清：**commit 是本地记录；push 是上传分支；合并是集成代码；部署是运行版本；上线是对用户开放并验证结果。

## 六、提测和 Bug 闭环

- [ ] 提测时带上版本、环境、入口、账号获取方式、数据准备、范围和自测证据。
- [ ] 说明数据库、配置、接口、消息和第三方变化。
- [ ] Bug 有复现步骤、预期与实际、版本、时间、必要日志与影响。
- [ ] 修复先确认根因，补针对性验证，关联提交和修复版本。
- [ ] 测试回归通过后按流程关闭；残留问题有决策与负责人。
- [ ] 产品或业务方验收的是最终候选版本的真实能力。

## 七、发布准备

- [ ] 发布单对应明确需求、提交、构建与不可变制品标识。
- [ ] 确定执行人、放行人、时间、影响范围和观察人员。
- [ ] 数据库迁移顺序、配置、密钥、网络、证书、回调都准备齐全。
- [ ] 明确发布方式：停机、滚动、蓝绿、灰度或功能开关。
- [ ] 旧版本与新结构/数据兼容；回退限制写清。
- [ ] 备份和恢复路径已按风险要求验证。
- [ ] 新功能的日志、技术指标、业务指标与告警可用。
- [ ] 约定暂停放量、回退、前向修复和数据处理的条件。
- [ ] 生产验证的账号、数据与外部副作用范围可控。

## 八、部署、上线和观察

- [ ] 核对目标环境与版本，逐步执行并记录结果。
- [ ] 检查健康状态、启动日志、流量与资源。
- [ ] 走通关键业务，核对数据库、异步结果和必要对账。
- [ ] 将错误率、延迟、积压和业务成功率与基线比较。
- [ ] 观察到足够样本与业务周期后，决定继续放量或结束观察。
- [ ] 更新发布结果、版本说明、运行手册和任务状态。
- [ ] 临时日志、权限和开关有清理安排，遗留问题有负责人。

**完成口径：**程序运行、接口返回、异步终态、用户验收是不同证据，按需求逐一确认。

## 九、出现故障

1. 确认影响范围与严重程度，通知公司约定的负责人。
2. 保留关键时间、版本、指标、日志、业务编号和近期变更。
3. 采取已知可控的止损措施：暂停放量、关闭入口或开关、限流、回退兼容版本等。
4. 按证据定位入口、应用、数据库、缓存、MQ、第三方或基础设施。
5. 验证恢复，检查积压和业务终态；服务恢复后继续核对受影响数据。
6. 补永久修复、回归用例、复盘行动和负责人。

**关键边界：**回退程序不撤销已经执行的退款；恢复整库可能覆盖合法新交易；未知结果不能用新的业务单号盲目重试。

## 十、优化和维护

- [ ] 优化目标有业务背景和基线：慢在哪里、频率多高、影响多少用户。
- [ ] 根据证据定位 SQL、锁、N+1、线程/连接池、GC、缓存、消息或外部服务。
- [ ] 一次改动有明确假设，使用可比较负载验证正确性与收益。
- [ ] 压测报告写明机器、数据、负载、延迟、错误、瓶颈和余量。
- [ ] 扩容前确认真正瓶颈，评估数据库连接、配额和下游承受能力。
- [ ] 定期处理依赖升级、证书、密钥轮换、备份恢复、容量和费用。
- [ ] 改进形成可追踪任务；废弃能力有迁移、存量处理、归档和权限回收。

## 遇到什么问题，先去哪里

| 问题 | 先检查或找谁 |
| --- | --- |
| 需求说法不一致 | 需求正文与评审结论；产品/业务负责人 |
| 不知道代码在哪改 | 页面请求、调用链、同模块最近变更；模块负责人 |
| 项目启动不了 | 构建/运行日志、版本、profile、依赖连通；带教/平台支持 |
| 前后端联调失败 | 请求实际地址、环境、参数、身份、响应与 traceId |
| CI 红了 | 失败阶段与日志，区分代码断言失败和环境失败 |
| 上线后接口变慢 | 发布前后指标、慢链路、数据库等待、连接与线程池 |
| 页面显示成功但业务未完成 | 任务表、退款单、MQ 积压、回调与对账 |
| 第三方超时 | 业务单号和官方查询/幂等协议，先明确结果是否未知 |
| 不知道能否发版 | 测试结论、发布单和公司放行责任人 |
| 线上数据不对 | 影响范围、外部事实、受控数据修复与核对流程 |

每个任务最后留下这六项就很有价值：**需求 → 约束 → 方案 → 实现 → 验证 → 遗留问题**。它们既能帮助你交付，也能让下一位同事接得住。
