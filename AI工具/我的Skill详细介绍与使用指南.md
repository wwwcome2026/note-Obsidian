## 如何调用与提供材料

Skill 是带有说明和可选脚本、参考资料的可复用工作流程。系统通常先看到名称和描述，需要使用时再读取正文；用户可以明确点名，也可以让任务描述匹配技能用途。[官方说明](https://learn.chatgpt.com/docs/build-skills)

在这份文档中，示例都采用“使用技能名，完成具体任务”的写法，复制到对话即可表达意图。支持技能选择器的界面也可以选择对应条目；Codex CLI 与 IDE 扩展的官方说明支持通过 `/skills` 或 `$` 提及技能。插件条目的显示名可能带命名空间，以下每项都会保留本次会话名称。

建议把提示词写成：

```text
使用【Skill 名称】完成【具体任务】。
输入：【文件、目录、材料或链接】
要求：【内容边界、风格、格式、必须保留的部分】
交付：【产物类型和保存位置】
验证：【希望实际检查的内容】
```

不必一次指定大量 Skill。例如“美化这份简历”通常由 resume-beautify 主导，文档渲染由相关能力配合；为所有任务强行套入完整开发流程反而会增加无关步骤。

本文的示例是用法示范，不代表这些动作已执行。需要外部应用时，仍以该次任务实际可调用工具、账号授权和运行环境为准。

## 需求分析与开发流程

### brainstorming｜需求澄清与方案设计

**来源：用户 Skill · 会话名称：`brainstorming`**

把模糊想法整理成可执行的设计，先理解目标、约束和取舍，再进入实现。

- **适合什么时候用：** 准备做新功能、新组件或较大的行为调整，但需求和方案尚未定下来。
- **给它什么材料：** 目标用户、现有项目、希望改变的行为、必须保留的内容，以及时间或技术约束。
- **通常怎样处理：** 先判断属于可行性探索、局部改动还是架构设计；阅读背景，澄清关键问题，比较方案，再确定设计。复杂需求会形成设计文档，后接 writing-plans。
- **最终得到什么：** 明确的方案、边界和验收目标；较大任务还会生成规格文档。
- **需要留意什么：** 本地版本包含实施前确认设计的要求，因此可能先给出方案。已有明确授权和更高优先级指令仍需遵守；它本身不代表代码已实现。

**可以这样说：**

> 使用 brainstorming，帮我梳理一个 Spring Boot 校园报修功能。先明确角色、状态流转和验收标准，给我两个可行方案。

依据：[本地 SKILL.md](<C:/Users/34029/.codex/skills/brainstorming/SKILL.md>)。

### writing-plans｜编写实施计划

**来源：用户 Skill · 会话名称：`writing-plans`**

把已确认的需求拆成开发者可以逐项执行的实施步骤。

- **适合什么时候用：** 需求已经清楚，改动涉及多个文件或多个有依赖的任务，需要知道先改哪里、怎样验证。
- **给它什么材料：** 确认后的需求或规格、仓库位置、技术栈、兼容性要求与完成标准。
- **通常怎样处理：** 识别文件职责和接口边界，拆解任务，列出具体文件、实现步骤、测试命令和预期结果，最后核对计划覆盖情况。
- **最终得到什么：** 实施计划 Markdown；本地默认位置为项目中的 docs/superpowers/plans/。
- **需要留意什么：** 写计划不等于执行计划。原说明引用的 executing-plans、subagent-driven-development 当前位于停用目录，不能默认当成已启用的后续能力。

**可以这样说：**

> 使用 writing-plans，根据这份分页接口需求写实施计划，列出 Controller、Service、Mapper 的修改位置与验证步骤。

依据：[本地 SKILL.md](<C:/Users/34029/.codex/skills/writing-plans/SKILL.md>)。

### planning-with-files｜用文件记录长任务进度

**来源：用户 Skill · 会话名称：`planning-with-files`**

将任务计划、发现和执行记录保存到文件，便于长任务续做与回看。

- **适合什么时候用：** 资料较多、步骤较多、可能跨多轮对话，或需要避免重复调查的工作。
- **给它什么材料：** 目标、工作目录、已有材料和最终交付物。
- **通常怎样处理：** 建立 task_plan.md、findings.md、progress.md；推进任务时记录发现、状态和错误，恢复工作时先读取记录。
- **最终得到什么：** 持续更新的计划、事实记录与进度日志。
- **需要留意什么：** 它主要管理执行过程，不替代 writing-plans 的实施设计。短问题或简单单文件改动通常不需要引入整套记录。

**可以这样说：**

> 使用 planning-with-files，整理项目中的登录鉴权链路，把调查发现和未确认问题记录下来，最后生成中文说明。

依据：[本地 SKILL.md](<C:/Users/34029/.codex/skills/planning-with-files/SKILL.md>)。

### test-driven-development｜测试驱动开发

**来源：用户 Skill · 会话名称：`test-driven-development`**

通过先写会失败的测试，再实现功能，建立需求与验证之间的对应关系。

- **适合什么时候用：** 新增业务行为、修复可复现缺陷、对关键逻辑重构。
- **给它什么材料：** 行为要求、输入输出示例、边界条件、现有测试框架。
- **通常怎样处理：** 先写能表达预期行为的测试并确认失败原因；写最小实现让测试通过；在保持通过的前提下整理代码。
- **最终得到什么：** 功能实现、行为测试和实际执行结果。
- **需要留意什么：** 测试应验证业务行为，不只是复述实现；已有绿色测试不能证明修复前确实能捕获问题。任务中的测试范围还需服从实际风险和上层要求。

**可以这样说：**

> 使用 test-driven-development，为优惠券过期判断补充实现，先覆盖到期前、到期时和到期后三种情况。

依据：[本地 SKILL.md](<C:/Users/34029/.codex/skills/test-driven-development/SKILL.md>)。

### systematic-debugging｜系统化排查问题

**来源：用户 Skill · 会话名称：`systematic-debugging`**

先找根因，再修改代码或配置，减少凭猜测反复尝试。

- **适合什么时候用：** 启动失败、接口异常、性能下降、测试失败、集成失效等问题。
- **给它什么材料：** 完整报错、复现步骤、预期与实际表现、近期变更、相关日志。
- **通常怎样处理：** 收集证据并复现，比较正常与异常路径，提出可证伪假设，通过小范围实验验证，再修复并回归。
- **最终得到什么：** 根因判断、证据、最小修复以及验证结果。
- **需要留意什么：** 外部服务、权限或环境问题可能只能先缩小范围。没有充分证据时应保留未知，不能把一次偶然成功当成根因已确认。

**可以这样说：**

> 使用 systematic-debugging，排查这个接口为什么偶发超时。先读取日志和调用链，验证假设后再改配置。

依据：[本地 SKILL.md](<C:/Users/34029/.codex/skills/systematic-debugging/SKILL.md>)。

### requesting-code-review｜发起代码审查

**来源：用户 Skill · 会话名称：`requesting-code-review`**

让独立审查者根据需求和差异检查实现，尽早发现遗漏和缺陷。

- **适合什么时候用：** 较大功能完成、重要重构完成、准备合并变更。
- **给它什么材料：** 需求或计划、变更说明、代码差异，以及可用时的基线与目标提交。
- **通常怎样处理：** 整理审查上下文，按本地说明请求代码审查子代理；核对需求覆盖、实现质量和风险，再处理重要问题。
- **最终得到什么：** 按严重程度组织的审查意见、位置和修复建议。
- **需要留意什么：** 需要环境支持相应的代理能力。审查不等于实际运行测试，也不包含自动合并或发布授权。

**可以这样说：**

> 使用 requesting-code-review，审查当前订单接口改动，重点看重复提交、事务边界和需求遗漏，给出具体文件位置。

依据：[本地 SKILL.md](<C:/Users/34029/.codex/skills/requesting-code-review/SKILL.md>)。

### receiving-code-review｜核实并处理审查意见

**来源：用户 Skill · 会话名称：`receiving-code-review`**

收到他人的修改建议后，先验证是否适合当前项目，再决定如何修改。

- **适合什么时候用：** 收到 PR 评论、同事审查意见或另一轮 AI 审查结果。
- **给它什么材料：** 原始评论、涉及代码、项目约束与相关测试。
- **通常怎样处理：** 读懂建议，核对真实实现和调用情况，判断是否会破坏兼容性；对成立的意见逐项处理，对不成立的意见给出技术理由。
- **最终得到什么：** 逐条处理结果、代码修正和必要的反驳依据。
- **需要留意什么：** 重点是正确处理意见，不是重新发起审查；模糊建议需要澄清，不能机械照改。

**可以这样说：**

> 使用 receiving-code-review，核对这五条评论，先区分真实缺陷、风格建议和不适用项，再修改成立的问题。

依据：[本地 SKILL.md](<C:/Users/34029/.codex/skills/receiving-code-review/SKILL.md>)。

### verification-before-completion｜完成前验证

**来源：用户 Skill · 会话名称：`verification-before-completion`**

要求完成声明建立在刚执行的检查结果上，明确哪些结论已得到证据支持。

- **适合什么时候用：** 准备宣称任务完成、问题已修复、测试通过或准备提交时。
- **给它什么材料：** 原始需求、最终改动和能够证明结果的命令或检查方法。
- **通常怎样处理：** 确定每项结论需要什么证据，运行检查，查看退出状态和结果，再逐项核对需求。
- **最终得到什么：** 有依据的完成报告、检查结果和仍未验证的边界。
- **需要留意什么：** 构建通过不证明所有业务行为正确；结构检查不能替代视觉检查。它是一项验收流程，不是万能测试工具。

**可以这样说：**

> 使用 verification-before-completion，核对这次修改的需求覆盖、相关测试和最终文件，再告诉我哪些已验证、哪些还没有。

依据：[本地 SKILL.md](<C:/Users/34029/.codex/skills/verification-before-completion/SKILL.md>)。

### documents｜Word 文档创建与编辑

**来源：插件 Skill · 会话名称：`documents:documents`**

创建、修改、批注或修订 DOCX，兼顾内容、可编辑结构和页面布局。

- **适合什么时候用：** 技术说明、报告、方案书、已有 Word 文档编辑，以及面向 Google Docs 的文档交付。
- **给它什么材料：** 源文件或材料、受众、目标格式、模板、页数和必须保留的内容。
- **通常怎样处理：** 按任务读取或修改文档，生成可编辑产物，再渲染页面检查分页、溢出、表格和字号，发现问题后调整。
- **最终得到什么：** 通常为 DOCX；按需提供已生成并验证的 PDF。
- **需要留意什么：** 需要对应文档运行时和渲染依赖。Google Docs 原生交付还需要相应连接器；仅有此 Skill 不代表已能访问云端文档。普通 Obsidian Markdown 不必走 Word 流程。

**可以这样说：**

> 使用 documents，把这些项目说明整理成可编辑 Word 技术文档，保留代码和表格，交付前检查分页。

### pdf｜PDF 阅读、生成与检查

**来源：插件 Skill · 会话名称：`pdf:pdf`**

读取、生成和检查 PDF，也处理带可填写字段的 AcroForm 表单。

- **适合什么时候用：** 提取 PDF 内容、生成固定版式材料、检查分页、填写已有 PDF 表单。
- **给它什么材料：** 源 PDF 或内容、目标页面规格、需要提取或填写的范围。
- **通常怎样处理：** 提取文字或检查字段，生成或修改文件，再渲染页面核对显示效果；表单还要验证字段值与外观是否一致。
- **最终得到什么：** PDF、提取内容或表单填写结果。
- **需要留意什么：** PDF 是固定版式，转成 Word 不保证无损；只有提取到文字不能证明视觉布局完整。是否需要 OCR 取决于文件是否为扫描件及可用工具。

**可以这样说：**

> 使用 pdf，提取这份说明书的重点和目录，并检查输出 PDF 是否有文字截断或空白页。

依据：[本地 SKILL.md](<C:/Users/34029/.codex/plugins/cache/openai-primary-runtime/pdf/26.905.11957/skills/pdf/SKILL.md>)。

### spreadsheets｜表格文件与数据分析

**来源：插件 Skill · 会话名称：`spreadsheets:Spreadsheets`**

创建或修改表格文件，处理公式、格式、图表、汇总和重新计算。

- **适合什么时候用：** 制作 XLSX、分析 CSV/TSV、修正公式，或在连接条件具备时处理 Google Sheets。
- **给它什么材料：** 数据文件、字段含义、计算规则、期望的工作表结构与图表。
- **通常怎样处理：** 设计工作簿结构，导入数据，建立公式与样式，计算并核对结果，再检查展示效果。
- **最终得到什么：** 表格文件、汇总分析和图表；云端产物取决于相应连接是否可用。

## 常用组合示例

以下组合按任务需要选择，不要求每次全部执行。

### 开发一个 Java 业务功能

需求不清时用 brainstorming；确认后用 writing-plans 拆解。实现关键业务逻辑时结合 test-driven-development，较大改动完成后用 requesting-code-review，最后用 verification-before-completion 核对证据。跨多轮任务可同时使用 planning-with-files 记录状态。

> 帮我为现有 Spring Boot 项目增加分页查询。先核对已有接口和分页规范，需求明确后给出必要计划并实施，验证边界条件，最后报告实际执行的检查。

### 排查一个难复现问题

systematic-debugging 负责调查和小范围实验；找到根因后，为可稳定复现的行为建立回归验证；verification-before-completion 负责核对最终结果。

> 排查这个接口偶发返回空列表的问题。先比较成功与失败请求，保留复现证据，找到根因后再改，并验证原问题。

### 整理知识材料和演示内容

humanizer-zh 可帮助调整表达；知识长文可交给 knowledge-2-web；浏览器演讲用 guizang-ppt-skill；需要可编辑 PPTX 时用 Presentations。需要图片时再按实际工具与配置选择 imagegen 或文章配图流程。

> 将这份技术总结改成自然、清楚的中文，然后制作 8 页可编辑 PPTX。保留技术事实，不新增未经确认的数据。

### 美化求职简历

resume-beautify 主导版式与正文保留，documents 负责文档结构和渲染相关能力。若还要求改写项目描述，再单独明确允许改写的范围，不把美化理解为重写经历。

> 美化这份 Word 简历，保留全部经历与日期，调整标题、分隔线和间距；检查正文一致性与分页，输出中文命名的副本。

### 建立可复用的个人工作流

找现成能力用 find-skills；安装指定目标用 skill-installer。自定义流程用 skill-creator；保存成品风格用 template-creator；需要组织成插件时再使用 plugin-creator。

> 把我已经确认的项目周报格式做成个人模板，保留栏目和样式，下次只替换当周内容，不发布到公共市场。
